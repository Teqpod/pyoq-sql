Migration lifecycle

Keeping snapshots and generated types aligned after schema changes.

PyOQ reads schemas but does not create them. Your migration tool changes the database. After that change succeeds, refresh the schema snapshot and the generated package in that order.

The lifecycle

Generation may read the snapshot, so recording first is part of the contract. Generating before the snapshot changes can reproduce the old package and make the update look complete when it is not.

One hook for both steps

Python
from pyoq.migrations import after_migration_at

outcome = after_migration_at(project_root)
print(outcome.describe())

If configuration is already loaded, use after_migration(configuration). Both functions record the selected profile and then run normal generation. They use the same validation, ownership manifest, and atomic replacement as the command line.

Django

Django generation reads migration state and does not contact the database. Run it after writing migrations:

Terminal
python manage.py makemigrations
python manage.py pyoq_codegen

To make that automatic, opt in through settings:

Python
INSTALLED_APPS = [
    "pyoq.django",
    # project applications follow
]

PYOQ = {
    "codegen_directory": "app/schema",
    "codegen_package": "app.schema",
    "codegen_after_makemigrations": True,
}

Application order matters because PyOQ supplies an explicit override of Django’s makemigrations command. Put pyoq.django before applications that could provide the same command. The original Django command runs first. Generation runs only after it successfully writes migration files, and is skipped for Django’s check and dry-run modes.

migrate applies migrations to a database. It does not regenerate because the generated package describes migration state, which should already have been reviewed with the migration files.

Alembic

Alembic covers this in full, including what goes wrong. Call the hook after context.run_migrations() succeeds:

Python
from pyoq.migrations import after_migration_at

with connectable.connect() as connection:
    context.configure(connection=connection, target_metadata=target_metadata)
    with context.begin_transaction():
        context.run_migrations()

after_migration_at(project_root)

Do not use an Alembic post-write hook for this. That hook runs when a revision file is created, before the revision has changed the database, so reflection would record the old schema.

A deployment pipeline

When production does not contain code-generation tooling or credentials, make the generated package and snapshot build artifacts:

  1. Apply the migration in an integration environment.
  2. Run the migration hook or the snapshot and generation commands.
  3. Run pyoq drift and pyoq generate --check.
  4. Run the application’s type checks and tests.
  5. Deploy the already reviewed generated package with the application.

Whether a deployment migrates before or after application rollout depends on your compatibility strategy. PyOQ does not make a breaking schema change safe. Use expand-and-contract migrations when old and new application versions may run together.

Failure behavior

Snapshot and package replacement are atomic independently. If recording fails, the previous snapshot stays intact and generation does not run. If generation fails, the newly recorded snapshot remains, while the previous generated package stays intact. Rerun the hook after correcting the cause.

See Snapshots and drift for recording and comparison details, and Generating your types for ownership rules.
