Frameworks

Django

Running on the connection Django already has open.

PyOQ borrows Django’s connection rather than opening a pool beside it. Two pools against one database is two views of what has been committed, and the point of running inside Django is that there is one.

Terminal
pip install "pyoq-sql[django]"

Settings

Python
INSTALLED_APPS = ["pyoq.django", ...]

PYOQ = {
    "codegen_directory": "app/schema",
    "codegen_package": "app.schema",
}
SettingMeans
codegen_directorywhere the generated package is written, relative to the project root
codegen_packageits importable name
project_rootoptional; defaults to BASE_DIR
codegen_layoutflat by default, or profiles for one package per database alias
databasesaliases and optional generated package names in profile layout
codegen_after_makemigrationsoptional; regenerate whenever makemigrations writes a migration

For several Django databases, make the output directory and package name bases:

Python
PYOQ = {
    "codegen_layout": "profiles",
    "codegen_directory": "app/generated",
    "codegen_package": "app.generated",
    "databases": {
        "default": {"codegen_name": "database"},
        "reporting": {},
    },
}

This writes app.generated.database and app.generated.reporting. An alias is used as its package directory by default. codegen_name replaces it when a different valid Python package segment is clearer.

Generate

Terminal
python manage.py pyoq_codegen
python manage.py pyoq_codegen catalog          # one app
python manage.py pyoq_codegen --database reporting
python manage.py pyoq_codegen --all-databases
python manage.py pyoq_codegen --all-databases --check
python manage.py pyoq_codegen --all-databases --dry-run
python manage.py pyoq_codegen --check          # fails when out of date
python manage.py pyoq_codegen --dry-run

No database is contacted. The schema comes from your migration files. The alias chooses the dialect and is passed through Django’s allow_migrate routers, so each generated package contains the models eligible for that database. Put --check in CI: it needs no credentials.

--database updates only that alias package and its ownership manifest. --all-databases loads and validates every configured alias before replacing the shared package base once. A failure for any alias leaves every existing generated package unchanged. The two options cannot be combined.

Generate after makemigrations

Set codegen_after_makemigrations to True to opt in. pyoq.django must appear before project applications in INSTALLED_APPS, because Django selects the first installed override of a management command. Django writes migration files first, then PyOQ regenerates for the same app labels and database alias. In profile layout it regenerates every alias listed in PYOQ["databases"] as one atomic operation, because the migration state changed for the project as a whole.

Generation does not run when makemigrations is asked only to check or perform a dry run. See Migration lifecycle for the full ordering.

In a view

Python
from pyoq.django import DjangoOperations
from pyoq.dsl import using
from app.schema.tables import TITLES

def list_titles(request):
    rows = (
        using(DjangoOperations())
        .select_from(TITLES)
        .order_by(TITLES.ID)
        .fetch_all()
    )
    return JsonResponse({"titles": rows.to_dicts()})

DjangoOperations() holds no connection. It resolves one per statement, and costs about two microseconds to build. Create it per request or keep one at module scope; both are fine.

Multiple databases

Python
DjangoOperations("reporting")               # by alias
DjangoOperations.for_model(Report)          # ask your routers
DjangoOperations.for_model(Report, write=True)

Routing is a question about a model, because that is all a router is given.

Transactions

Python
database = DjangoOperations()

with database.atomic():
    database.execute(...)

database.on_commit(lambda: notify())

atomic() covers this alias. Django’s own transaction.atomic() covers the default one unless told otherwise, so a statement here against another alias would get no transaction at all and no sign of it.

PyOQ never commits or rolls back on Django’s connection. The block that opened a transaction ends it, and here that block is Django’s.

Values match what the ORM writes

A value is bound through the field Django itself would use. Without a native type Django stores a UUID as hex and a duration as microseconds, and reads a naive datetime as local time, so a row PyOQ writes is a row Model.objects.filter(...) finds.

Pass a UUID. Never str(value), never .hex.

Types follow your models

A column is typed by what the field means, not the column it asks for. JSONField reads back as JSON, UUIDField as a UUID, DurationField as a timedelta, even on SQLite, where all three are stored as text or integers.

Policies

Python
from pyoq.policies import SoftDelete, TenantScope, governed

scoped = governed(DjangoOperations(), [
    TenantScope("tenant_id", request.tenant_id),
    SoftDelete("deleted_at"),
])

Async views

Python
from asgiref.sync import sync_to_async

rows = await sync_to_async(read_titles)()

Django’s connections are synchronous. Wrap the call rather than reaching for the asynchronous chain, which expects a pool of its own.

Keep the complete database unit of work inside the wrapped function. Returning a stream, transaction, or borrowed connection across the sync boundary leaves its owner on the wrong thread.
