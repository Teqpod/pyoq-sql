Configuration

Every setting PyOQ reads, and where it reads it from.

Configuration lives in pyproject.toml, under [tool.pyoq]. A server profile can keep its connection and pool settings as separate values. Each value is literal unless the entire value has the ${VARIABLE_NAME} form.

Configuration
[tool.pyoq]
codegen-directory = "generated/database"
codegen-package = "application.database"
selected-profile = "default"

[tool.pyoq.profiles.default]
dialect = "postgres"
host = "database.internal"
port = 5432
database = "${POSTGRES_DATABASE}"
username = "${POSTGRES_USERNAME}"
password = "${POSTGRES_PASSWORD}"
minimum-pool-size = 1
maximum-pool-size = 8
pool-checkout-timeout = 3.0

[tool.pyoq.profiles.testing]
dialect = "sqlite"
database-path = "database/testing.sqlite"

Top level

SettingMeans
codegen-directorywhere the generated package is written, relative to the project root
codegen-layoutflat for one package, or profiles for one package per database profile
codegen-packageits importable name
selected-profilewhich profile a command uses when none is named
schema-snapshotwhere the recorded schema is kept, relative to the project root, and inside it
profilesthe profiles themselves

When omitted, codegen-directory and codegen-package both default to pyoq_generated, and selected-profile defaults to default. Profiles are never invented; at least one must be configured.

codegen-layout defaults to flat, which preserves the established directory and import path exactly. In profiles layout, codegen-directory and codegen-package are bases. Each profile is generated below them.

codegen-directory must stay inside the project root. A path that escapes it is refused, because generation replaces what is there and a path that walks out of the project is a way to replace something else.

A profile

SettingMeans
dialectsqlite, postgres, or mysql
dsna literal connection string, or a complete ${VARIABLE_NAME} environment reference
dsn-environmentthe legacy form containing only an environment variable name
database-patha SQLite file, relative to the project root
hostserver host, defaulting to localhost
portserver port, defaulting to 5432 for PostgreSQL or 3306 for MySQL
databaseserver database name
usernameserver user name
passwordoptional server password
minimum-pool-sizeconnections opened with the pool, defaulting to 0
maximum-pool-sizemaximum connections in this process, defaulting to 5
pool-checkout-timeoutseconds to wait for a connection, defaulting to 30.0
codegen-namepackage segment below the generation base; defaults to the profile name
schema-snapshotthis profile’s recorded schema in profile layout

One package per database

Use profile layout when one application connects to more than one database:

Configuration
[tool.pyoq]
codegen-layout = "profiles"
codegen-directory = "generated"
codegen-package = "generated"
selected-profile = "default"

[tool.pyoq.profiles.default]
codegen-name = "database"
dialect = "mysql"
database = "${MYSQL_DATABASE}"
username = "${MYSQL_USERNAME}"
password = "${MYSQL_PASSWORD}"
schema-snapshot = "schemas/database.json"

[tool.pyoq.profiles.analytics]
dialect = "postgres"
dsn = "${ANALYTICS_DATABASE_URL}"
schema-snapshot = "schemas/analytics.json"

This produces generated.database and generated.analytics. A codegen-name must be one valid Python package segment and must be unique across profiles. Profile names that are already valid package segments need no override.

The top-level schema-snapshot belongs to flat layout. Profile layout keeps a snapshot on each profile so two databases cannot accidentally read the same record merely because they share one project.

Every way to name a database

A profile names its database in exactly one of the ways below. They cannot be combined: a profile that mixes them is refused rather than resolved in some order you would have to know.

Every part named separately. What a deployment that already holds its parts separately can use directly.

Configuration
[tool.pyoq.profiles.default]
dialect = "postgres"
host = "database.internal"
port = 5432
database = "shop"
username = "shop_service"
password = "${POSTGRES_PASSWORD}"

database and username are required once any structured field is present. host defaults to localhost, and port to 5432 for PostgreSQL or 3306 for MySQL. PyOQ percent-encodes the credentials and the database name while building the connection, so a password containing @, # or / needs no escaping from you.

One connection string.

Configuration
[tool.pyoq.profiles.default]
dialect = "mysql"
dsn = "mysql://shop_service:p%40ssw0rd@localhost:3306/shop"

Here the escaping is yours: those same characters divide a URL, so a password containing one has to be percent-encoded before it goes in.

A connection string kept out of the file. The same thing, with nothing secret committed:

Configuration
[tool.pyoq.profiles.default]
dialect = "mysql"
dsn = "${MYSQL_DATABASE_URL}"

A variable name, the older form. dsn-environment holds the name of a variable and never a connection string:

Configuration
[tool.pyoq.profiles.default]
dialect = "mysql"
dsn-environment = "MYSQL_DATABASE_URL"

It stays accepted for projects already using it. dsn = "${MYSQL_DATABASE_URL}" says the same thing in the form every other setting uses.

A SQLite file.

Configuration
[tool.pyoq.profiles.testing]
dialect = "sqlite"
database-path = "database/testing.sqlite"

The path is resolved against the project root, must stay inside it, and is opened read-only while inspecting. A SQLite profile can use dsn instead, and cannot use the structured fields. A schema source provided by an integration, such as Django migration state, can use a profile that names no database at all, because it never inspects a live one.

Literal, or read from the environment

Every profile setting is a literal unless the whole value has the ${VARIABLE_NAME} form. Nothing is looked up unless it asks to be.

WrittenUsed as
"shop_service"that text
"PATH"that text, not the variable of that name
"${DB_USER}"the value of DB_USER
"$DB_USER"that text, because there are no braces
"pre${DB_USER}"refused

A value that is part reference and part text is refused rather than read as a literal. Read as a literal it would be used as typed, so a password meant to come from the environment would be sent as the text that asks for it, and the first sign of the mistake would be a server refusing the connection.

A reference to a variable that is not set is an error, not an empty value. PyOQ does not load .env files: export the variables before running a command. Do not commit a literal that carries credentials.

Pool settings

Pool settings are per profile, and take a number or a reference resolving to one. They apply to whichever way the database was named.

Configuration
[tool.pyoq.profiles.default]
dialect = "postgres"
dsn = "${POSTGRES_DATABASE_URL}"
minimum-pool-size = 1
maximum-pool-size = "${POSTGRES_POOL_SIZE}"
pool-checkout-timeout = 3.0

The framework-free MySQL application follows this profile through generation, runtime settings, pool ownership, repositories, transactions, and process shutdown.

Opening the selected profile

The same profile can own the application database lifecycle:

Python
from pathlib import Path

from pyoq import connect
with connect(
    profile="default",
    project_root=Path.cwd(),
) as database:
    run_application(database)

Omit profile to use selected-profile. Pool settings from that profile are used automatically. An explicit pool_policy=PoolPolicy(...) replaces all profile pool settings for that call. This synchronous convenience API supports all three dialects. Framework integrations and asynchronous applications use their dedicated lifecycle APIs.

The project root

The project root is the containment boundary, not a search result. PyOQ does not walk upward looking for configuration. Commands default it to the current working directory and read pyproject.toml there unless --config names another file inside the same root.

Configured output, snapshots, SQLite database paths, and relative configuration paths must stay inside this directory. This prevents a mistaken command from replacing files in a parent or unrelated project.

Selecting a profile

selected-profile is the default for every command. Override it for one run:

Terminal
pyoq inspect --project-root . --profile testing
pyoq generate --project-root . --profile analytics
pyoq generate --project-root . --all-profiles

The override does not edit configuration. It only selects one of the profiles already declared in the file.

--all-profiles is available only to generate in profile layout and cannot be combined with --profile.

Reading it yourself

Python
from pathlib import Path
from pyoq.config import load_configuration

configuration = load_configuration(Path.cwd())
database_url = configuration.active_profile.resolve_dsn()
if database_url is not None:
    connect_value = database_url.reveal()

A resolved secret is a value you have to ask to see. reveal() is a deliberate call, so a connection string never lands in a log through an ordinary repr.

Unknown settings are refused

A setting PyOQ does not recognise raises UnknownConfigurationSettingError rather than being ignored. A misspelled key that is quietly skipped is a setting that silently does nothing, and the usual way to find out is in production.

Under Django

There is no TOML. Django settings hold the same facts:

Python
PYOQ = {
    "codegen_directory": "app/schema",
    "codegen_package": "app.schema",
}

Django profile layout uses database aliases instead of TOML profile names:

Python
PYOQ = {
    "codegen_layout": "profiles",
    "codegen_directory": "app/generated",
    "codegen_package": "app.generated",
    "databases": {
        "default": {"codegen_name": "database"},
        "reporting": {},
    },
}

The alias becomes the generated directory unless codegen_name replaces it. python manage.py pyoq_codegen --all-databases publishes every configured alias atomically.

See Django for the full list.

What is deliberately not configurable

Generated output is not formatted to taste, and the generated directory is owned entirely by the generator. Both are so that regenerating is safe: a directory PyOQ shares with hand-written files is a directory it cannot replace.
