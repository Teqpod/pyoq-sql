Expressions and conditions

Comparisons, arithmetic, functions, and how they stay typed.

These examples take three things as given:

  • database is an open database, from a pool you opened or from the framework you are inside
  • dsl is using(database)
  • TITLES and its columns come from your generated package

Your first query builds all three from nothing.

Every column descriptor is a typed expression. What you can do with it, and what you can compare it to, follows from the type the database gave it.

Comparisons

Python
TITLES.ID.eq(1)
TITLES.ID.ne(1)
TITLES.PRICE.gt(Decimal("10.00"))
TITLES.PRICE.ge(Decimal("10.00"))
TITLES.PRICE.lt(Decimal("10.00"))
TITLES.PRICE.le(Decimal("10.00"))
TITLES.PRICE.between(Decimal("5.00"), Decimal("15.00"))
TITLES.PRICE.not_between(Decimal("5.00"), Decimal("15.00"))
TITLES.ID.in_(1, 2, 3)
TITLES.ID.not_in(1, 2, 3)
TITLES.COUNTRY.is_null()
TITLES.COUNTRY.is_not_null()
TITLES.COUNTRY.is_distinct_from("US")

Compare a Decimal column to a string and the type checker stops you. The scalar families also have to line up: comparing text to a number raises ExpressionTypeError while you are building, not when the database complains.

Booleans

Python
TITLES.WITHDRAWN.is_true()
TITLES.WITHDRAWN.is_false()

Combining conditions

A condition is itself an expression, so it combines with methods or with operators. Both produce the same tree.

Python
TITLES.PRICE.gt(10).and_(TITLES.WITHDRAWN.is_false())
TITLES.ID.eq(1).or_(TITLES.ID.eq(2))
TITLES.WITHDRAWN.is_true().not_()
SQL
SELECT "titles"."id" FROM "titles"
WHERE (("titles"."price" > ?)
   AND (SUBSTR("titles"."name", 1, LENGTH(?)) = ?))
Python
(
    dsl.select(TITLES.ID).from_(TITLES).where(
        TITLES.PRICE.gt(Decimal("10"))
    .and_(TITLES.NAME.starts_with("A"))
    )
)

The operators &, |, and ~ do the same thing:

Python
predicate = TITLES.ID.gt(0) & TITLES.NAME.starts_with("A")
either = TITLES.ID.eq(1) | TITLES.ID.eq(2)

where() accepts one condition. Combine the conditions before passing them so the grouping remains explicit.

Text

Python
TITLES.NAME.like("A%")
TITLES.NAME.not_like("A%")
TITLES.NAME.starts_with("A")
TITLES.NAME.ends_with("Guide")
TITLES.NAME.contains("Guide")
TITLES.NAME.lower()
TITLES.NAME.upper()
TITLES.NAME.length()
TITLES.NAME.concat(" (revised)")

Arithmetic

Python
TITLES.PRICE.add(1)
TITLES.PRICE.subtract(1)
TITLES.PRICE.multiply(2)
TITLES.PRICE.divide(2)
TITLES.PRICE.modulo(2)
TITLES.PRICE.negate()

The operators +, -, *, / do the same thing.

Dates, times, and durations

Python
from pyoq.query import DatePart

TITLES.RELEASED.extract(DatePart.YEAR)
TITLES.RELEASED.add_duration(timedelta(days=7))
TITLES.RELEASED.subtract_duration(timedelta(days=7))
TITLES.RELEASED.difference(TITLES.WITHDRAWN_ON)

Aggregates

Python
from pyoq.query import average, count, maximum, minimum, sum_

count()                    # int
count(TITLES.PAGES)        # int, counting the non-null
sum_(TITLES.PRICE)         # Decimal | None
average(TITLES.PRICE)      # Decimal | None
minimum(TITLES.RELEASED)   # date | None
maximum(TITLES.RELEASED)   # date | None

The optional is not caution. An aggregate over no rows genuinely has no value, and a type that hid that would be lying to you.

Choosing a value

case() reads its branches in order and stops at the first that holds.

SQL
SELECT "titles"."name",
       CASE WHEN ("titles"."price" > ?) THEN ?
            WHEN ("titles"."price" > ?) THEN ?
            ELSE ? END
  FROM "titles"
Python
from pyoq.query import case

dsl.select(
    TITLES.NAME,
    case()
    .when(TITLES.PRICE.gt(Decimal("50")), "premium")
    .when(TITLES.PRICE.gt(Decimal("10")), "standard")
    .otherwise("budget"),
).from_(TITLES)

The whole expression takes its type from the first result, so a later branch that disagrees is refused where you write it, not when the query runs.

otherwise() closes the case with a value for every remaining row, and the result is not nullable. end() closes it without one, and the result is T | None, because SQL answers null for a row that matched nothing.

SQL
SELECT CASE WHEN ("titles"."price" > ?) THEN ? END FROM "titles"
Python
dsl.select(case().when(TITLES.PRICE.gt(Decimal("50")), "premium").end()).from_(
    TITLES
)

The first value that is not null

SQL
SELECT COALESCE("titles"."name", ?) FROM "titles"
Python
from pyoq.query import coalesce

dsl.select(coalesce(TITLES.NAME, "untitled")).from_(TITLES)

When the column is nullable and the fallback is not, coalesce() drops the None from the type: a nullable Expression[str | None] becomes ComputedExpression[str], and the row you read back needs no null check.

nullif() is the mirror image, answering null when its two arguments agree. It turns a placeholder value into a real absence:

SQL
SELECT NULLIF("titles"."name", ?) FROM "titles"
Python
from pyoq.query import nullif

dsl.select(nullif(TITLES.NAME, "")).from_(TITLES)

The widest and the narrowest

SQL
SELECT MAX("titles"."price", ?) FROM "titles"
Python
from pyoq.query import greatest

dsl.select(greatest(TITLES.PRICE, Decimal("0"))).from_(TITLES)
SQL
SELECT MIN("titles"."price", ?) FROM "titles"
Python
from pyoq.query import least

dsl.select(least(TITLES.PRICE, Decimal("100"))).from_(TITLES)

These compare across arguments in one row, which is not what MIN and MAX do as aggregates across rows. SQLite has no GREATEST or LEAST and spells the row-wise form MAX and MIN over several arguments, which is what you see above. On PostgreSQL and MySQL the same two lines emit GREATEST and LEAST.

Everything on this page is an expression like any other, so it can be selected, compared, ordered by, grouped by, or nested inside another one. Values reach them bound, never as SQL text.

Asking for another type

SQL
SELECT CAST("titles"."price" AS NUMERIC) FROM "titles"
Python
from pyoq.query import cast

dsl.select(cast(TITLES.PRICE, Decimal)).from_(TITLES)

You name a Python type; the dialect names its own. A cast is the only computed expression that declares what it answers with, so it is the only one whose promise survives the driver: cast(x, Decimal) gives you a Decimal on every dialect, even where the driver would have handed back a float.

Refused means exactly that: the query does not compile. SQLite would happily accept CAST(x AS DATE) and answer with an integer, because an unfamiliar type name falls back to storage affinity there. Emitting it would promise a date and hand back something else, so PyOQ will not.

MySQL is asked for DECIMAL(65, 30) rather than DECIMAL, because a bare one means DECIMAL(10, 0) there and would answer 123 for 123.45. These names were taken from running servers, not from a specification.

A type no database type answers to is refused where you write it:

Python
cast(TITLES.NAME, set)  # TypeError: set is not a cast target

Measuring a row against its neighbours

An aggregate collapses a group into one row. A window leaves the rows alone and gives each one an answer computed from the rows around it.

SQL
SELECT "titles"."name",
       ROW_NUMBER() OVER (PARTITION BY "titles"."publisher_id"
                          ORDER BY "titles"."price" DESC)
  FROM "titles"
Python
from pyoq.query import row_number

dsl.select(
    TITLES.NAME,
    row_number().over().partition_by(TITLES.PUBLISHER_ID).order_by(
        TITLES.PRICE.desc()
    ),
).from_(TITLES)

The clauses read in the order SQL writes them: the function, then the window it looks through, then how that window is divided and ordered. A window with no partition_by() covers every row.

SQL
SELECT "titles"."name", RANK() OVER (ORDER BY "titles"."price" DESC)
  FROM "titles"
Python
from pyoq.query import rank

dsl.select(TITLES.NAME, rank().over().order_by(TITLES.PRICE.desc())).from_(
    TITLES
)

row_number() counts from one and breaks ties arbitrarily. rank() gives tied rows the same position and leaves a gap after them, dense_rank() gives them the same position and no gap, and ntile(n) says which of n equal buckets a row falls in.

A running total, and the row before

Any aggregate can be taken over a window instead of over a group, through the same over(). The rows stay as they are and each one gets the aggregate of the window around it:

SQL
SELECT "titles"."name", SUM("titles"."price") OVER (ORDER BY "titles"."id" ASC)
  FROM "titles"
Python
dsl.select(TITLES.NAME, sum_(TITLES.PRICE).over().order_by(TITLES.ID)).from_(
    TITLES
)

lag() and lead() read the value that many rows back or ahead. Past the edge of the window there is no such row, so both are typed T | None:

SQL
SELECT "titles"."name", LAG("titles"."price", ?) OVER (ORDER BY "titles"."id" ASC)
  FROM "titles"
Python
from pyoq.query import lag

dsl.select(TITLES.NAME, lag(TITLES.PRICE).over().order_by(TITLES.ID)).from_(
    TITLES
)

A window orders rows the way a query does, using the same terms and the same rules, so asking for nulls last inside a window works on every dialect just as it does outside one. Window functions need SQLite 3.25 or later, and a build without them refuses the query rather than emitting SQL it cannot run.

Reading a value out of the window

first_value, last_value and nth_value answer with a value one of the rows already held, so each is typed by the column it reads and may answer with nothing:

Python
from pyoq.query import cume_dist, first_value, last_value, nth_value, percent_rank

first_value(TITLES.PRICE).over().order_by(TITLES.ID)
nth_value(TITLES.PRICE, 2).over().order_by(TITLES.ID)
percent_rank().over().order_by(TITLES.PRICE)
cume_dist().over().order_by(TITLES.PRICE)

last_value reads the last row the frame reaches, and without a frame a window ends at the current row, so it answers with the current row’s value until the frame is widened.

Narrowing the window

Python
from pyoq.query import current_row, following, preceding, unbounded_preceding

sum_(TITLES.PRICE).over().order_by(TITLES.ID).rows(
    unbounded_preceding(), current_row()
)
sum_(TITLES.PRICE).over().order_by(TITLES.PRICE).range_(preceding(1), following(1))

rows counts rows, range_ counts by value so equal rows come together, and groups counts peer groups. exclude leaves rows out that the frame would otherwise reach. MySQL has neither groups nor exclude and refuses both.

Naming a window

Repeating a partition and an order beside every function is how they come to disagree. Declare it once and say which window each function reads through:

Python
from pyoq.query import named_window, rank, row_number

ranked = named_window("ranked").partition_by(TITLES.PUBLISHER_ID).order_by(
    TITLES.PRICE
)
dsl.select(row_number().over(ranked), rank().over(ranked)).from_(TITLES).window(
    ranked
)

A window read through but never declared is refused while the query is compiled, and a window declared by a query is refined where it is declared rather than at one of its readers.

Null treatment is in none of the three. IGNORE NULLS is refused by PostgreSQL, MySQL and SQLite alike, so PyOQ offers no way to ask for it rather than one that could only ever raise.

Comparing several values as one

A composite key is one key. row() compares columns side by side against tuples, instead of an OR of ANDs you have to reassemble while reading:

SQL
SELECT "titles"."name" FROM "titles"
 WHERE (("titles"."publisher_id", "titles"."name") IN ((?, ?), (?, ?)))
Python
from pyoq.query import row

dsl.select(TITLES.NAME).from_(TITLES).where(
    row(TITLES.PUBLISHER_ID, TITLES.NAME).in_((1, "A Guide"), (2, "A Sequel"))
)

The tuples are checked against the columns by position, so this is caught where you write it, not when the query runs:

Python
row(TITLES.PUBLISHER_ID, TITLES.NAME).in_((1, 2))     # 2 is not a name
row(TITLES.PUBLISHER_ID, TITLES.NAME).eq(("a", 1))    # wrong way round
row(TITLES.PUBLISHER_ID, TITLES.NAME).in_((1, "a", 2))  # too wide

in_(), not_in(), eq(), ne(), gt(), ge(), lt(), and le() are all available. The ordering comparisons compare left to right the way SQL orders a row value, so (tenant, id) > (1, 100) means every row of a later tenant, plus the rows of tenant one after id 100. That is what makes keyset pagination over a composite key a single predicate.

A row value is two columns or more, because SQL reads a single bracketed value as that value. Every value travels bound, as in any other predicate.

Looking for membership in the rows of another query is a semi join, not a row value.

Reading inside a JSON value

A path is steps, not text:

Python
TITLES.METADATA.json_text("author", "country")
TITLES.METADATA.json_text("tags", 0)
TITLES.METADATA.json_length("tags")
TITLES.METADATA.json_has("author", "verified")
TITLES.METADATA.json_contains({"author": {"city": "London"}})

A string step is a member and an integer step is an element. Steps rather than text because the dialects genuinely disagree, and one of them disagrees silently: give PostgreSQL the $.a.b that SQLite and MySQL want and it looks for a member actually called $.a.b, finds nothing, and answers null without complaining. PyOQ writes each dialect’s own form.

json_get() answers with JSON; json_text() answers with what that JSON says and is typed str | None, so you get text on every dialect even where the driver would hand back the number it looked like.

AskedSQLitePostgreSQLMySQL
json_get-> '$.a.b'#> '{a,b}'JSON_EXTRACT
json_textJSON_EXTRACT#>> '{a,b}'CASE over JSON_UNQUOTE
json_lengthJSON_ARRAY_LENGTHJSONB_ARRAY_LENGTHJSON_LENGTH
json_hasJSON_TYPE(...) IS NOT NULL#> ... IS NOT NULLJSON_CONTAINS_PATH
json_containsrefused@>JSON_CONTAINS
json_keysJSON_EACH gatheredJSONB_PATH_QUERY_ARRAYJSON_KEYS

The path is a value, so it binds like any other and never enters the SQL. SQLite has no containment operator and refuses rather than emulating one. Asking any of this of a column that is not JSON is refused where you write it.

MySQL unquotes a JSON null into the four letters of its name, where the other two answer with no text at all, so PyOQ writes a CASE there and json_text means one thing everywhere. To tell a member holding null from a member that is absent, ask json_has: a member holding null is there on all three.

json_length measures an array. Counting the members of an object is json_keys().json_length(), which is portable where asking an object its length is not.

Changing a JSON value

Every one of these answers with a new document. Nothing is changed in place.

Python
TITLES.METADATA.json_set("author", "country", to="Ireland")
TITLES.METADATA.json_insert("author", "verified", to=True)
TITLES.METADATA.json_replace("tags", 0, to="python")
TITLES.METADATA.json_remove("draft")
TITLES.METADATA.json_merge({"author": {"city": "Cork"}})
TITLES.METADATA.json_concat({"author": {"city": "Cork"}})

json_merge and json_concat are two operations, not one, and the difference is what got them separated. Merging is merge-patch: a member given as null is removed, and an object inside an object is merged rather than replaced. Concatenating is one level: a member is replaced whole and a null is stored as a null.

MySQL and SQLite merge all the way down and have no one-level concatenation. PostgreSQL concatenates one level and has no merge-patch at all. Each is refused where the dialect has not got it, rather than quietly doing the other.

Building a JSON value

Python
from pyoq.query import json_agg, json_array, json_object, json_object_agg

json_object({"name": TITLES.NAME, "price": TITLES.PRICE})
json_array(TITLES.NAME, TITLES.PRICE)
json_agg(TITLES.NAME)
json_object_agg(TITLES.NAME, TITLES.PRICE)

The last two are aggregates, so they take a window through over() like any other. Reading a JSON array back as rows is a source rather than an expression:

Python
from pyoq.query import ELEMENT_COLUMN, json_elements

rows = json_elements(TITLES.METADATA.json_get("tags"), alias="tag")
dsl.select(rows.field(str, ELEMENT_COLUMN)).from_(rows)

Asking about an array

An array column is generated as tuple[T, ...], and these are typed by that element type:

Python
TITLES.TAGS.has("python")
TITLES.TAGS.lacks("draft")
TITLES.TAGS.contains_all(("python", "sql"))
TITLES.TAGS.overlaps(("python", "rust"))
TITLES.TAGS.contained_by(("python", "sql", "rust"))
TITLES.TAGS.element(0)
TITLES.TAGS.length()
TITLES.TAGS.append("rust")
TITLES.TAGS.prepend("sql")
TITLES.TAGS.without("draft")
TITLES.TAGS.replacing("draft", "final")
TITLES.TAGS.concat_array(("rust", "go"))
TITLES.TAGS.length_along(1)
TITLES.TAGS.dimensions()

Elements count from zero. The column reads back as a tuple, and a tuple counts from zero, so TAGS.element(0) is the same element as row.tags[0]. SQL counts an array from one; PyOQ writes that difference out rather than leaving you to remember it. Past the end there is no element, so the answer is null and the type is T | None.

length() is the same method that measures text: how long a thing is is one question whichever kind of thing it is. It counts every element; length_along(n) counts one dimension, and dimensions() says how many dimensions there are.

An array of arrays is read at one position per dimension, together, because PostgreSQL reads one subscript of a nested array as nothing at all:

Python
GRID.element(1, 0)

Building one starts from values rather than from a column:

Python
from pyoq.query import array_of

array_of("python", "sql")

An array built from no values has no element type, and no database will store a value whose type it cannot name, so that is refused where you write it.

Only PostgreSQL has an array type. SQLite and MySQL refuse these outright and point at JSON or a table of its own, rather than emulating an array they have not got.

Calling a function this database has

Every database grows functions the others have not got. Declare one once, and call it like any other expression:

Python
from pyoq.config import DatabaseDialect
from pyoq.query import vendor_function, vendor_predicate

similarity = vendor_function(
    float, "similarity", dialects=(DatabaseDialect.POSTGRES,)
)
starts_with = vendor_predicate(
    "starts_with", dialects=(DatabaseDialect.POSTGRES,)
)

dsl.select_from(TITLES).where(similarity(TITLES.NAME, "Ada").gt(0.3))

dialects says where the function exists. A compiler for any other database refuses the query rather than sending SQL that cannot run, so a mistake surfaces while you are writing rather than in production. A declaration naming no dialect is written everywhere, because saying nothing means you did not say.

vendor_function() answers with the type you give it. vendor_predicate() answers with a condition, so it composes with and_(), or_(), and where() like any other.

Arguments travel bound, exactly as everywhere else. The name is not a value, because no database takes a function name as a parameter, so it is written into the SQL and held to being a name: an identifier, optionally qualified by its schema. Anything else is refused where you declare it.

Reach for raw() instead when what you need is not a call at all, but a fragment of SQL with a shape of its own.

Ordering terms

Python
TITLES.PRICE.desc()
TITLES.NAME.asc()
TITLES.PAGES.desc().nulls_last()
TITLES.PAGES.asc().nulls_first()

Nulls go where you put them on every dialect. PostgreSQL and SQLite have a NULLS clause and use it. MySQL has none and sorts nulls first whichever way you sort, so PyOQ orders on whether the value is null before ordering on the value, which lands them in the same place. See Dialects.

Naming a column in the output

Python
from pyoq.query import alias

dsl.select(alias(count(), "total")).from_(TITLES)

The name matters when you read rows back as dictionaries: every column needs one, and PyOQ refuses to invent it.

When there is no helper

Python
from pyoq.query import raw, raw_condition

raw(int, "octet_length({column})", column=TITLES.NAME)
raw_condition("{column} @@ to_tsquery('guide')", column=TITLES.NAME)

You give the value type, because PyOQ cannot infer what your fragment returns. Anything interpolated through {} is a typed expression, never a value: values still bind as parameters, so a raw fragment is not a way around that. A dialect that does not accept raw fragments refuses them rather than passing them through.
