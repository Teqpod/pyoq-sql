Reading

Reading results

Asking for the shape you want at the end of the chain.

These examples take three things as given:

  • database is an open database, from a pool you opened or from the framework you are inside
  • dsl is using(database)
  • TITLES and its columns come from your generated package

Your first query builds all three from nothing.

A chain ends by saying how many rows you expect and what shape you want them in. Those are two separate questions, and PyOQ keeps them separate.

How many

Python
.fetch_all()        # a Result, holding every row
.fetch_one()        # exactly one Row, or an error
.fetch_optional()   # one Row, or None
.fetch_value()      # the single column of the single row

fetch_one raises NoResultError when there is nothing and MultipleResultsError when there is more than one. It never quietly takes the first, because that answers a question nobody asked.

Use fetch_optional when a missing row is an ordinary outcome, like a lookup by id that should become a 404.

What shape

Result shapes a collection. Row shapes one tuple. Both preserve the labels and can convert into an application type, while collection-only cardinality methods stay on Result.

Python
rows = dsl.select_from(TITLES).fetch_all()

rows.to_list()          # [(1, 'A Guide', Decimal('12.50')), ...]
rows.to_tuple()         # the same, as a tuple
rows.to_dicts()         # [{'id': 1, 'name': 'A Guide', ...}, ...]
rows.to_dict()          # exactly one row keyed, or an error
rows.into(TitlesRow)    # [TitlesRow(...), ...]
rows.map(lambda r: r[1])
rows.one()              # exactly one row
rows.first()            # the row at the front, or None
rows.labels             # ('id', 'name', 'price')
Python
row = dsl.select_from(TITLES).where(...).fetch_one()

row.to_dict()           # {'id': 1, 'name': 'A Guide', ...}
row.to_list()           # [1, 'A Guide', Decimal('12.50')]
row.to_tuple()          # (1, 'A Guide', Decimal('12.50')), typed as selected
row.into(TitlesRow)     # TitlesRow(...)
row.labels

A Row is a tuple. It unpacks, indexes, compares, and iterates exactly as it always did:

Python
identifier, name, price = row
row[0]
row == (1, "A Guide", Decimal("12.50"))

Building your own type

into spreads the row across a constructor in the order it was selected, which is the order the generated row type takes its arguments, so generated rows work without you arranging anything.

Python
@dataclass(frozen=True, slots=True)
class Title:
    identifier: int
    name: str

dsl.select(TITLES.ID, TITLES.NAME).from_(TITLES).fetch_all().into(Title)

A row that may be missing takes the type in the chain, so you do not have to test for None before you can build it:

Python
dsl.select_from(TITLES).where(...).fetch_optional_into(Title)   # Title | None

Unpacking a Row into a constructor, Title(*row), does not type check, because a generic tuple subclass spreads as object. Use into(Title), or Title(*row.to_tuple()) if you want the unpack form.

Dictionaries need names

to_dicts and to_dict refuse a row with an unnamed column rather than inventing a key. Give the column a name with alias:

Python
from pyoq.query import alias

dsl.select(alias(count(), "total")).from_(TITLES).fetch_all().to_dicts()

Iterating instead

A Result iterates and has a length, so it behaves as the sequence it is:

Python
for row in rows:
    ...

if rows:
    ...
len(rows)

For results too large to hold. See streaming.
