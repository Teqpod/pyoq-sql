Reference

Command line

Every command, and what it does.

Terminal
pyoq --version
pyoq generate --project-root .
pyoq inspect --project-root .
pyoq snapshot --project-root .
pyoq drift --project-root .

Every command takes --project-root, because that is what makes a run reproducible: the configuration, the generated directory, and any SQLite path are all resolved from it.

Every command, every option and every exit code is listed in pyoq commands, including pyoq-after-migration.

Common options

OptionDoes
--project-root PATHsets the directory all configured paths are contained in; defaults to the working directory
--config PATHreads a configuration file other than pyproject.toml; a relative path is resolved from the project root
--profile NAMEselects a profile for this command without changing selected-profile

Options belong after the subcommand:

Terminal
pyoq inspect --project-root . --profile reporting
pyoq generate --project-root . --config config/pyproject.toml --check

The project root is normally the directory containing pyproject.toml. In a Django project it is often the directory containing manage.py, but those two files do not have to be beside each other. Pass the directory that owns the PyOQ configuration.

generate

Writes the generated package from the schema the selected profile names.

Terminal
pyoq generate --project-root .
pyoq generate --project-root . --check
pyoq generate --project-root . --dry-run
pyoq generate --project-root . --profile reporting
pyoq generate --project-root . --all-profiles
FlagDoes
--checkwrites nothing; fails when the package is not up to date
--dry-runwrites nothing; reports what a run would create, update, or remove
--all-profilesgenerates every profile in profile layout as one atomic publication

--profile and --all-profiles cannot be combined. --all-profiles supports both --check and --dry-run, and reports each profile separately.

--check and --dry-run cannot be combined. They answer different questions, whether the package is current, and what a run would produce, and a command that quietly picked one would answer a question you did not ask.

snapshot

Records what the database holds in the file schema-snapshot names, which is what generation reads when there is no database to connect to.

Terminal
pyoq snapshot --project-root .

Recording the same database twice writes the same bytes, so the file changes only when the schema does. Without schema-snapshot set there is nowhere to write, and the command says so rather than choosing a path for you.

drift

Compares the recorded schema against the database and fails when they disagree.

Terminal
pyoq drift --project-root .

The answer names what moved in terms of the schema rather than of the file.

Text
1 schema difference(s): added column warehouse.public.parts.weight

inspect

Reports what PyOQ sees in the schema without writing anything: the tables, their columns and types, the keys, and the relations derived from them.

Terminal
pyoq inspect --project-root .

Useful when generated code is not what you expected and you want to know whether the problem is the schema or the generator.

Exit codes

CodeMeans
0success
1the command ran and failed
2invalid usage
3configuration could not be loaded
4the operation is unavailable, usually a missing extra

Distinct codes so a pipeline can tell “the schema drifted” from “the configuration is wrong” without reading the message.

Under Django

Use the management command instead. It reads your migration state and needs no database or credentials.

Terminal
python manage.py pyoq_codegen --check

In CI

YAML
- run: pyoq generate --project-root . --check

With schema-snapshot configured this needs no database credentials. It turns a forgotten regeneration into a failed build rather than a confusing runtime error later. Add pyoq drift in an environment that can reach the live database when the pipeline must also prove the recorded schema is current.
