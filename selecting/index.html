Selecting rows

Naming columns, taking every column, ordering, and limiting.

These examples take three things as given:

  • database is an open database, from a pool you opened or from the framework you are inside
  • dsl is using(database)
  • TITLES and its columns come from your generated package

Your first query builds all three from nothing.

Every read starts with what you want back, then where it comes from.

Inspect without executing

Any query built through using(database) can expose the SQL for that database’s dialect before it runs:

Python
query = (
    dsl.select(TITLES.ID, TITLES.NAME)
    .from_(TITLES)
    .where(TITLES.PRICE.gt(Decimal("10.00")))
)

print(query.sql())
compiled = query.compile()
print(compiled.parameters)

sql() returns SQL with placeholders. Values are not interpolated. Use compile() when the bound parameters, sensitive-parameter indexes, statement kind, or declared result types are also needed. Both methods are pure compilation: they do not check out a connection, execute, spend a query budget, or emit an execution event. They are synchronous on both the synchronous and asynchronous DSL.

Name the columns

SQL
SELECT "titles"."id", "titles"."name"
FROM "titles"
Python
dsl.select(TITLES.ID, TITLES.NAME).from_(TITLES)

The row type follows exactly: tuple[int, str]. Up to eight columns keep their per-position types.

from_ accepts the table descriptor directly. It also accepts an aliased source when you need one:

Python
from pyoq.query import table_source

dsl.select(TITLES.ID).from_(table_source(TITLES, alias="t"))

Or take the whole table

SQL
SELECT * FROM "titles"
Python
dsl.select_from(TITLES)

That selects every column the table declares. The generated table tells PyOQ their names, order, and value types so the result can be converted into the generated row type.

The SQL uses SELECT *. Regenerate and redeploy consumers with every schema change, and use an explicit .select(...) when the projection must remain stable while the table gains columns.

Since the order matches the generated row type’s arguments, into builds it:

Python
dsl.select_from(TITLES).fetch_all().into(TitlesRow)

Filtering

SQL
SELECT "titles"."id", "titles"."name"
FROM "titles"
WHERE ("titles"."price" > ?)
Python
(
    dsl.select(TITLES.ID, TITLES.NAME)
    .from_(TITLES)
    .where(TITLES.PRICE.gt(Decimal("10.00")))
)

Combine several conditions explicitly with & or and_():

Python
.where(TITLES.NAME.like("A%") & TITLES.WITHDRAWN.is_false())

See Expressions for OR, negation, and reusable conditions.

Ordering

Python
.order_by(TITLES.ID)
.order_by(TITLES.PRICE.desc(), TITLES.NAME.asc())

Where the dialect supports it, null placement is explicit:

Python
.order_by(TITLES.PAGES.desc().nulls_last())

Limiting

SQL
SELECT "titles"."id" FROM "titles"
ORDER BY "titles"."price" DESC
LIMIT ? OFFSET ?
Python
(
    dsl.select(TITLES.ID).from_(TITLES)
    .order_by(TITLES.PRICE.desc())
    .limit(20)
    .offset(40)
)

Grouping

Python
from pyoq.query import count, sum_

(
    dsl.select(TITLES.PUBLISHER_ID, count(), sum_(TITLES.PRICE))
    .from_(TITLES)
    .group_by(TITLES.PUBLISHER_ID)
    .having(count().gt(5))
)

count() is int; sum_ and average return an optional, because a group with no rows to add up has no sum.

Distinct

Python
dsl.select(TITLES.PUBLISHER_ID).from_(TITLES).distinct()

Naming a column in the output

SQL
SELECT COUNT(*) AS "total" FROM "titles"
Python
from pyoq.query import alias

dsl.select(alias(count(), "total")).from_(TITLES)

The name matters when you read rows back as dictionaries: every column needs one, and PyOQ refuses to invent it.

Order of the chain

The builder enforces it. where after order_by is a QueryStateError, not a query that quietly means something else. Defining a source twice is refused the same way.

Running it

Nothing above touched a database. The chain ends when you say what shape you want. That is Reading results.

When the package is out of date

A star widens with the table. If somebody adds a column and the generated package is not regenerated, the database answers with more columns than the statement projected, and PyOQ refuses the result rather than reading the old columns out of a wider row:

Text
QueryExecutionError: the database answered with 5 columns where the statement
projected 4; a generated package that no longer matches its schema reads a row
by the wrong columns, so regenerate it

Put pyoq generate --check in CI and this never reaches anybody.
