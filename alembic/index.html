Frameworks

Alembic

Keeping the snapshot and the generated package in step with your migrations.

Alembic owns the schema. PyOQ reads it. Nothing about that changes when you use both: Alembic writes and applies migrations exactly as it did, and PyOQ needs one thing from you, which is to be told when the database has moved.

There is no extra to install and no adapter to configure. PyOQ never opens a connection through Alembic and never takes part in a migration.

What has to happen, and in what order

After a migration is applied, two things are behind:

  1. The recorded schema snapshot, which still describes the old database.
  2. The generated package, which was generated from that snapshot.

They have to catch up in that order, because generation reads the snapshot. Doing it the other way regenerates the old package and makes the update look complete when it is not.

after_migration_at does both, in order.

Where to put it

In env.py, once the migrations have run

The project owns env.py, so this is the place with the most context.

Python
from pathlib import Path

from alembic import context
from pyoq.migrations import after_migration_at

PROJECT_ROOT = Path(__file__).resolve().parents[2]


def run_migrations_online() -> None:
    connectable = engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    with connectable.connect() as connection:
        context.configure(connection=connection, target_metadata=target_metadata)
        with context.begin_transaction():
            context.run_migrations()

    # The database has moved. Bring the snapshot and the package back in step.
    after_migration_at(PROJECT_ROOT)

Put it after the with block, not inside it. Inside, the migration has not committed yet, and reflection would read a schema no other connection can see.

Or as a step of its own

Terminal
alembic upgrade head && pyoq-after-migration

The command takes a project directory, or nothing and uses the working directory. && matters: if the upgrade fails there is nothing to catch up to.

Not as a post-write hook

This is the one thing that looks right and is not.

Configuration
# Do not do this.
[post_write_hooks]
hooks = pyoq
pyoq.type = console_scripts
pyoq.entrypoint = pyoq-after-migration

A post-write hook runs inside alembic revision, which writes a revision file. It does not apply one. The database at that moment is still whatever it was, so recording the schema there records the schema the migration is about to replace, and generates from it. The package would then describe the old database while the migration sits unapplied.

Alembic hands a hook the file it has just written, and that is how PyOQ notices: being given a file rather than a directory is refused, with a message saying so, rather than quietly recording the wrong schema.

What you get back

Python
outcome = after_migration_at(PROJECT_ROOT)
print(outcome.describe())

MigrationOutcome carries what each step reported, as recorded and generated, and describe() puts both on one line worth logging.

If your project has more than one profile, name the one the migration touched:

Python
after_migration_at(PROJECT_ROOT, selected_profile="primary")

A caller that already holds a Configuration can use after_migration instead, which takes it directly.

In a pipeline

Where production has no credentials and no code generation, make the snapshot and the generated package build artifacts instead:

  1. Apply the migration in an integration environment.
  2. Run pyoq-after-migration, or the hook from env.py.
  3. Run pyoq drift and pyoq generate --check.
  4. Run the type checks and the tests.
  5. Ship the reviewed package and snapshot.

Steps 3 and 4 are what catch a migration that changed something the code did not expect: --check fails when the generated package is not what the schema now implies, and the type checker fails where code still reads a column that moved.

What can go wrong

SymptomCause
The hook refuses, saying it was given a fileIt is wired as a post-write hook. Move it after alembic upgrade.
The snapshot records the pre-migration schemaThe call sits inside the begin_transaction() block, before the commit.
pyoq generate --check fails in CI after a migrationThe catch-up step did not run, or ran before the upgrade.
The package regenerated but is unchangedGeneration ran before the snapshot was re-recorded. after_migration_at does both in the right order.

See Migration lifecycle for the same ground without Alembic, and pyoq commands for what pyoq-after-migration exits with.
