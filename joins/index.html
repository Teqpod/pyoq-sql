Joins and set operations

Bringing tables together, and combining whole queries.

These examples take three things as given:

  • database is an open database, from a pool you opened or from the framework you are inside
  • dsl is using(database)
  • TITLES and its columns come from your generated package

Your first query builds all three from nothing.

Joining

Every join type is its own method, and the clause that qualifies it comes after, so the chain reads in the order SQL is written.

SQL
SELECT "titles"."name", "publishers"."name"
FROM "titles"
INNER JOIN "publishers"
  ON ("titles"."publisher_id" = "publishers"."id")
Python
(
    dsl.select(TITLES.NAME, PUBLISHERS.NAME)
    .from_(TITLES)
    .join(PUBLISHERS)
    .on(TITLES.PUBLISHER_ID.eq(PUBLISHERS.ID))
)

Every kind

SQLPyOQ
INNER JOIN t ON c.join(t).on(c) or .inner_join(t).on(c)
LEFT JOIN t ON c.left_join(t).on(c)
RIGHT JOIN t ON c.right_join(t).on(c)
FULL JOIN t ON c.full_join(t).on(c)
CROSS JOIN t.cross_join(t)
NATURAL JOIN t.natural_join(t)
NATURAL LEFT JOIN t.natural_left_join(t)
NATURAL RIGHT JOIN t.natural_right_join(t)
NATURAL FULL JOIN t.natural_full_join(t)

A cross join and a natural join take no qualifier, so they finish the chain on their own. Every other kind must be told how the rows line up before it is a query at all: a join left unqualified is not a statement you can run or read, and the type checker will say so.

Three ways to qualify one

SQL
SELECT "titles"."id" FROM "titles"
LEFT JOIN "publishers" USING ("id")
Python
(
    dsl.select(TITLES.ID)
    .from_(TITLES)
    .left_join(PUBLISHERS)
    .using("id")
)

USING matches columns both tables name the same way, and takes the columns themselves as well as their names:

Python
.using(TITLES.PUBLISHER_ID)
.using("tenant_id", "region")

NATURAL goes further and matches on every column they share, which is convenient and worth being careful with: adding a column to either table changes what the join means.

Filtering by whether a related row exists

A semi join keeps a left row when the right side has a match, without adding right-side columns. An anti join keeps it when no match exists:

Python
active_publishers = (
    dsl.select(PUBLISHERS.ID, PUBLISHERS.NAME)
    .from_(PUBLISHERS)
    .semi_join(TITLES)
    .on(TITLES.PUBLISHER_ID.eq(PUBLISHERS.ID))
)

publishers_without_titles = (
    dsl.select(PUBLISHERS.ID, PUBLISHERS.NAME)
    .from_(PUBLISHERS)
    .anti_join(TITLES)
    .on(TITLES.PUBLISHER_ID.eq(PUBLISHERS.ID))
)

PyOQ renders these as EXISTS and NOT EXISTS, which avoids duplicating a left row when several right rows match.

Joining on a key you already declared

Generation writes a descriptor for every foreign key, in both directions. A join can use it rather than restating the columns:

Python
from generated.relations import CATALOG_TITLE_PUBLISHER_ID_FORWARD

(
    dsl.select_from(TITLES)
    .left_join(PUBLISHERS)
    .on_key(CATALOG_TITLE_PUBLISHER_ID_FORWARD)
)

That compiles to the same ON you would have written, built from what the schema says. A composite key becomes one equality per column, joined with AND, which is the shape that is easy to get wrong by hand.

What a dialect will not do

A dialect that cannot do a join refuses it rather than emitting something close. SQLite has neither a RIGHT nor a FULL join, and MySQL has no FULL join, so asking for one there raises UnsupportedQueryError while you build. See Dialects, where every operation is listed per dialect.

Aliasing

A table joined to itself needs a name for each side:

Python
editor = table_source(PUBLISHERS, alias="editor")
printer = table_source(PUBLISHERS, alias="printer")

(
    dsl.select(TITLES.NAME)
    .from_(TITLES)
    .join(editor)
    .on(TITLES.EDITOR_ID.eq(editor.field(int, "id")))
    .join(printer)
    .on(TITLES.PRINTER_ID.eq(printer.field(int, "id")))
)

Subqueries

Python
recent = (
    select(TITLES.PUBLISHER_ID)
    .from_(TITLES)
    .where(TITLES.RELEASED.gt(date(2020, 1, 1)))
    .as_subquery("recent")
)

(
    dsl.select(PUBLISHERS.NAME)
    .from_(PUBLISHERS)
    .join(recent)
    .on(PUBLISHERS.ID.eq(recent.field(int, "publisher_id")))
)

Correlated lateral sources

An ordinary derived table is independent of the row beside it. A lateral source may refer to that row, which is useful for a top result per parent:

Python
publisher = table_source(PUBLISHERS, alias="publisher")
title = table_source(TITLES, alias="title")
publisher_id = publisher.field(int, "id")

latest = (
    select(title.field(str, "name").as_("latest_name"))
    .from_(title)
    .where(title.field(int, "publisher_id").eq(publisher_id))
    .order_by(title.field(int, "id").desc())
    .limit(1)
    .as_lateral("latest")
)

query = (
    select(publisher_id, latest.field(str, "latest_name"))
    .from_(publisher)
    .cross_join(latest)
)

PostgreSQL and MySQL execute lateral sources. SQLite refuses them during compilation.

Common table expressions

Python
totals = (
    select(TITLES.PUBLISHER_ID, alias(count(), "total"))
    .from_(TITLES)
    .group_by(TITLES.PUBLISHER_ID)
    .as_common_table("totals")
)

dsl.select(...).with_(totals).from_(totals)

Recursive common tables declare their typed columns before either term is built. Reusing the column object to read the recursive source preserves its type in autocomplete and static checks:

Python
from pyoq.query import bind, column, recursive_table, select

number = column("n", int)
walk = recursive_table("walk", number)
walk_definition = walk.define(
    select(bind(1)),
    select(walk.field(number).add(1))
    .from_(walk)
    .where(walk.field(number).lt(5)),
)
numbers = select(walk.field(number)).with_(walk_definition).from_(walk_definition)

All supported dialects execute this form. A mismatch between either term and the declared row is rejected before compilation.

Combining whole queries

Python
left = select(TITLES.NAME).from_(TITLES)
right = select(PUBLISHERS.NAME).from_(PUBLISHERS)

left.union(right)       # distinct
left.union_all(right)   # every row
left.intersect(right)
left.except_(right)

Both sides must project the same number of columns with matching types. The type checker enforces it, because both sides carry their row type.

except_ has the trailing underscore because except is a Python keyword, the same reason from_ does.
