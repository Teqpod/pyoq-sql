Stored routines

Calling generated functions and procedures with catalog-derived types.

These examples take three things as given:

  • database is an open database, from a pool you opened or from the framework you are inside
  • dsl is using(database)
  • TITLES and its columns come from your generated package

Your first query builds all three from nothing.

PostgreSQL and MySQL catalogs can describe functions and procedures. Generation turns those definitions into typed Python callables in routines.py, including input types, defaults, overloads, and output parameters the dialect can carry.

Prefer generated calls. A manually named call is available for a routine that cannot be reflected, but then the catalog cannot protect its signature.

Functions are expressions

Python
from application.database.routines import calculate_total

query = (
    dsl.select(ORDERS.ID, calculate_total(ORDERS.ID))
    .from_(ORDERS)
    .order_by(ORDERS.ID)
)

A generated function accepts values or expressions of its declared input type and returns a ComputedExpression[T]. Use it in a projection, condition, ordering term, update value, or any other place an expression belongs.

Trailing database defaults become optional arguments. PostgreSQL overloads are represented with Python overloads when their arity distinguishes them. Calls that cannot be represented without ambiguity keep distinct generated names.

Procedures are statements

Python
from application.database.routines import record_note

result = database.execute(record_note(7, "checked"))

A procedure does not become an expression. Execute its generated Call through the bound context or operations object.

When the catalog declares OUT or INOUT parameters, the generated call carries their result tuple:

Python
outputs = database.one(measure_order(ORDER_ID))

The tuple positions and nullability follow the catalog. A procedure with no declared output returns only its execution result. MySQL procedures with OUT or INOUT parameters require session variables, which a single bound call cannot safely represent, so their generated callable raises UnsupportedQueryError before SQL is sent.

Manual calls

Use call() when the routine is intentionally outside the reflected schema:

Python
from pyoq.query import call

statement = call("record_note", 7, "checked", schema="operations")
database.execute(statement)

Arguments are bound parameters. The routine and schema names are SQL structure, so PyOQ validates and quotes them as identifiers.

If a manual procedure returns rows, declare the result descriptors explicitly:

Python
rows = database.many(call("read_notes").returning(NOTES.ID, NOTES.BODY))

Those descriptors are your type claim. Generation is safer because its claim comes from the catalog and changes when the catalog changes.

Database-specific scalar functions

A scalar function unavailable to reflection can still be declared once:

Python
from pyoq.config import DatabaseDialect
from pyoq.query import vendor_function

similarity = vendor_function(
    float,
    "similarity",
    dialects=(DatabaseDialect.POSTGRES,),
)

The declared Python type becomes the expression’s result type. The dialect list causes every other compiler to reject it. Argument arity and types are not known for a manual declaration, so keep it behind a small, typed application function when callers need a stricter contract.
