LLM agent guide

Contracts, architecture, source routing, and safe change rules for coding agents.

This page is the compact project context for LLM coding agents. Use it to identify the correct subsystem and its contracts before reading implementation files. It is intentionally explicit about boundaries that are easy to infer incorrectly.

When working inside the repository, read the root AGENTS.md first. The current user request and repository instructions govern how work is performed. This page explains the product and where its behavior lives.

Stable project facts

FactContract
DistributionInstall pyoq-sql; import pyoq
PythonPython 3.11 or later
DatabasesSQLite, PostgreSQL, and MySQL
Async executionPostgreSQL and MySQL only
FrameworksDjango, FastAPI, Sanic, and standalone services
Schema authorityThe database schema or an explicit schema snapshot
Query modelImmutable, fully typed statement trees
ValuesBound parameters, never interpolated into SQL structure
Generated codeDeterministic, typed, Ruff-clean, and owned by its manifest
RuntimePortable Python with an optional native acceleration path

PyOQ is database first and SQL centered. It is not an ORM, does not maintain a session-wide identity map, does not lazily load relations, and does not decide when application data is written. It reads schema facts, generates Python contracts, builds SQL statements, compiles them for a dialect, and executes them through explicit operations.

System model

Keep these stages separate. Generation does not execute queries. Query builders do not open connections. Compilers do not own pools. Framework adapters do not reimplement schema inspection or execution.

Generated API model

Generated packages expose two related names for a table:

  • A class such as Account, which owns generated insert and update builders.
  • A table descriptor such as ACCOUNT, which owns typed column descriptors.
Python
from application.database import ACCOUNT, Account
from pyoq.query import insert_into

values = Account.builder().name("Example").build()

statement = (
    insert_into(ACCOUNT, ACCOUNT.NAME)
    .values(values.name)
    .returning(ACCOUNT.ID, ACCOUNT.NAME)
)

Builders produce immutable values and never perform I/O. Required insert fields are represented by staged builder types, so build() becomes available only when the required values have been supplied. Generated files must be changed through the schema model and renderer, never by editing generated output.

Generation has two layouts. Flat layout writes one package and is the default. Profile layout writes one package per database below a shared base. Each has an isolated manifest. An all-profile run prepares every schema and publishes the base once, so no profile may write before every plan has validated.

See Generating your types, Inserting rows, and Updating and deleting for complete application examples.

Query and execution model

There are two public construction styles:

  • Functions in pyoq.query build immutable statements without a database.
  • using(operations) creates a bound fluent context whose terminal methods execute through those operations.

Framework-free synchronous applications should enter connect() once at their composition root. It can load the selected pyproject.toml profile or accept a direct data source with Dialect. The yielded Database is a DslContext with transactions, streaming, and pool statistics. The context owns and closes its pool. Structured server profiles keep host, port, database, username, password, and pool limits in one configuration source. A complete ${VARIABLE_NAME} value resolves from the process environment; every other string is literal. Do not enter the context for every repository operation.

Use the pure query API for reusable statements, compilation tests, advanced features, and code that should not know how connections are owned. Use the bound context for application code that benefits from a single fluent chain.

Result cardinality is explicit:

OperationContract
fetch_all() or many()Zero or more rows
fetch_optional() or one_or_none()Zero or one row; duplicates fail
fetch_one() or one()Exactly one row; absence and duplicates fail
execute()Execute a write and return its execution result

Transactions yield an operations object. Execute through that yielded object so every statement uses the transaction’s connection:

Python
with database.transaction() as transaction:
    transaction.execute(first_statement)
    transaction.execute(second_statement)

The asynchronous form uses async with and awaited operations. There is no asynchronous SQLite executor. Read Asynchronous execution and Transactions and streaming before changing these paths.

Dialect contract

Supporting a feature means more than producing plausible SQL. A complete dialect feature has:

  1. A typed public construction API.
  2. An immutable query or schema representation.
  3. Correct dialect rendering or explicit emulation.
  4. A precise rejection when the dialect cannot support it.
  5. Parameter adaptation and result decoding where values cross the driver.
  6. Tests against the real database when server behavior matters.

Do not claim a shared capability because one compiler accepts its syntax. SQLite is not evidence for PostgreSQL or MySQL behavior. Locking, routines, arrays, JSON operations, returning clauses, concurrency, and driver conversion require the relevant dialect contract tests.

Framework routing

Framework adapters own lifecycle integration, not database semantics.

FrameworkOwnership modelGuide
DjangoUses the connection and transaction Django already ownsDjango
FastAPIOpens pools in lifespan and injects typed operationsFastAPI
SanicOpens pools per worker and exposes request-scoped accessSanic
Standaloneconnect() opens once and closes onceStandalone services

Shared reflection, generation, compilation, decoding, pooling, and transaction behavior belongs in the core package. An adapter should translate framework lifecycle and configuration into those shared services.

Django profile generation maps configured database aliases to core generation profiles. One alias owns one generated package and manifest. An all-database run must use the shared atomic profile publication path rather than looping over single-profile writes.

Invariants an agent must preserve

  • Query trees and schema value objects remain immutable.
  • Application values travel as bound parameters.
  • Identifiers come from trusted schema descriptors or validated identifier APIs, not from ordinary bound values.
  • Builders remain free of hidden I/O.
  • One schema fact has one canonical representation.
  • Generation remains deterministic and atomically replaces only manifest-owned files.
  • Public APIs remain fully typed under strict Mypy and Pyright.
  • Unsupported behavior raises a precise public error before partial execution.
  • Pools, streams, transactions, and framework resources have explicit owners and bounded lifetimes.
  • Performance changes are accepted only with measured throughput and memory evidence while the portable runtime remains functional.

Common incorrect assumptions

Do not infer these behaviors:

  • where() does not accept several independent arguments. Compose conditions with & or | and pass one condition.
  • Joins use .join(source).on(condition), not an on= argument to join().
  • Stream sizing is configured with StreamPolicy, not a batch_size keyword on the stream method.
  • A transaction context yields transaction-bound operations. Do not execute its statements through the outer database object.
  • SyncDatabase and AsyncDatabase are lifecycle wrappers. Their operations member performs database work.
  • select_from(TABLE) renders SELECT *. Prefer explicit columns when schema changes must not alter the result shape.
  • Generated builders live on the generated table class; typed fields live on the generated table descriptor instance.
  • SQLite support does not imply asynchronous SQLite execution.
  • Generated files are outputs, not an alternative source of schema truth.

Safe change procedure

  1. Identify the owning package and its mirrored tests.
  2. Read the public guide and exported names for the affected contract.
  3. Reproduce the current behavior with the smallest relevant test.
  4. Change the canonical model before adapters or generated output.
  5. Add dialect-specific rendering, rejection, decoding, and live evidence as required.
  6. Update generated behavior in its renderer and regenerate fixtures.
  7. Update public documentation and runnable examples in the same change.
  8. Run the narrow tests first, then the repository checks required by the affected boundary.

Never silently narrow a requirement to make an existing test pass. Record a missing capability as unsupported until its entire contract is implemented.

Verification map

Use the smallest checks that provide fast feedback, then run the complete gates for the change boundary:

Terminal
uv run --no-sync ruff check .
uv run --no-sync ruff format --check .
uv run --no-sync mypy
uv run --no-sync pyright
uv run --no-sync pytest

Native changes also require Rust formatting, lint, and tests. Performance changes require the maintained benchmark contracts. Documentation changes require the link, import, SQL-pair, Astro, production build, and search-index checks described in Testing applications.

Completion rule

A feature is complete only when its public typing, immutable representation, dialect behavior, parameter handling, result decoding, execution evidence, documentation, and failure behavior agree. Passing a narrow unit test proves only that narrow contract.

When evidence and prose disagree, treat executable repository evidence as the current behavior, correct the prose, and raise any product-level mismatch as a separate change rather than documenting behavior that does not exist.
