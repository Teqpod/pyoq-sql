Snapshots and drift

Recording what the database holds, and noticing when it moves.

A snapshot is the one record of what a database holds. Written to a file it becomes something you can read in a diff, and something PyOQ can generate from when there is no database to connect to.

Record the schema

Tell PyOQ where the record lives, then write it.

Configuration
[tool.pyoq]
schema-snapshot = "schema.json"

That is the flat-layout form. Profile layout keeps each record beside the profile it describes:

Configuration
[tool.pyoq]
codegen-layout = "profiles"

[tool.pyoq.profiles.default]
dialect = "mysql"
schema-snapshot = "schemas/database.json"

[tool.pyoq.profiles.analytics]
dialect = "postgres"
schema-snapshot = "schemas/analytics.json"
Terminal
pyoq snapshot

Recording the same database twice writes the same bytes, so the file changes only when the schema does. That is what makes it worth reviewing: a diff on it is a diff of your schema, not of the order a catalog happened to answer in.

The file is written beside its destination and moved into place, so a reader never sees half a snapshot, and a write that fails leaves the previous record exactly as it was.

Generate without a database

With schema-snapshot set, generation reads the file instead of connecting.

Terminal
pyoq generate

Nothing else changes. The same pipeline serves both, and it does not know which one it got. This is what lets a continuous integration job check that the generated package is current without credentials, without a database, and without writing anything:

Terminal
pyoq generate --check
pyoq generate --all-profiles --check

That command reads. It does not repair what it finds.

Notice when the schema moves

Terminal
pyoq drift

The answer is in terms of the schema, not of the file, so it names the column that moved rather than the line that differs.

Text
1 schema difference(s): added column warehouse.public.parts.weight

Things are matched by name and then by value. A renamed table therefore reads as one removed and one added, rather than as a change to something that is no longer there.

pyoq drift exits non-zero when the record and the database disagree, so it sits in the same place in a pipeline as any other check.

After a migration

A migration changes the schema. That makes two things wrong at once: the generated package is stale, and the recorded snapshot describes a database that no longer exists. One call puts both back in step:

Python
from pyoq.migrations import after_migration_at

after_migration_at(project_root)

The snapshot is written first and the package is generated second. The other order would generate from the schema that has just been replaced.

If you already hold a Configuration, call after_migration with it instead. The Migration lifecycle guide shows where this belongs in Django, Alembic, and deployment workflows.

What a comparison looks at

Every fact a snapshot records is compared, not only its columns. A key, a relation, an index, a check, a comment, a piece of metadata and the capabilities the database reported are all part of the recorded schema, and a change to any of them is drift.

Named things are reported by name, so a key that appeared is reported as that key. Everything else a container holds is reported as the container, because a comment on a table has no name of its own to give.

The comparison works by standing a container’s named children aside and comparing what is left, rather than by checking a written list of attributes. A fact added to the schema model is therefore compared from the day it exists, which is what keeps the check exhaustive as the model grows.

What a failed recording leaves

A snapshot is written beside where it is going and moved into place, so a reader never sees half of one and the snapshot already there survives a failure byte for byte.

A recording can fail while the staged file is being written, while it is being closed, or as it is moved. Whichever it is, the staged file goes with it, so a failure leaves the directory as it found it rather than beside a partial file nobody will claim. A cleanup that cannot happen either is not allowed to replace the reason the recording failed.

Where a snapshot may be written

schema-snapshot is relative to the project root and has to stay inside it. An absolute path, a path that climbs out with .., and a symbolic link that points out of the project are all refused when the configuration is read, because recording a schema writes and replaces a file and that file belongs to the project. It is the same rule the generated directory and a SQLite database path are held to.

In profile layout the same containment rule applies to every profile’s snapshot. A top-level snapshot is refused there because it would leave several databases sharing one ambiguous record.
