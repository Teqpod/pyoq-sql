Releasing

What a release is held to, what it is built from, and how one is withdrawn.

This page is the process every release follows. It was written before the first one rather than after it, so it describes what is done rather than what happened to be done.

What is supported

What a release is tested against, which is a different statement from what it happens to work on:

DeclaredTested against
Python3.11 and newer3.11, 3.12, 3.13, 3.14
Django4.2 up to but not including 74.2 and 6.1, the ends of that range
PostgreSQLno minimum is claimed17
MySQLno minimum is claimed8.4
SQLitewhatever the Python build carriesthe runner’s own
Operating systemsLinux on x86-64 and aarch64, glibc and musl; macOS on x86-64 and Apple silicon; Windows on x86-64 and aarch64a wheel is built for every one; five of the eight are also installed and imported

Three of the eight platform wheels are built and not run: both musl targets, because a musl wheel cannot be imported on the glibc runner that builds it, and macOS on x86-64, because the runner that builds it is Apple silicon. Those three are checked for their contents and their metadata like every other wheel, and are not claimed to have been executed.

No minimum server version is claimed for PostgreSQL or MySQL, because none has been established by testing one. Individual features do state what they need, next to the feature: RETURNING needs SQLite 3.35, window functions need SQLite 3.25, ordering inside a collection needs SQLite 3.44, and one MySQL spelling needs 8.0.19. Where a server cannot do something, it is refused with a message saying so rather than answered with something else.

The compiled extension is built against the stable ABI for Python 3.11, so one binary serves every supported version.

Where no native wheel matches a platform, the portable wheel installs. It carries no compiled code and runs the Python implementation of every kernel, so it needs no compiler. That is the fallback.

The source archive is not. It builds through the same backend the native wheels use, so installing it needs a Rust toolchain. It is for building from source deliberately, not for platforms that lack a wheel.

Where a version is decided

Each version this project pins is decided in one place, and nothing restates it without being held to it.

VersionDecided in
uvpyproject.toml, under [tool.uv], which uv reads and refuses to run against a mismatch
Rust toolchainrust-toolchain.toml, which the toolchain reads
Python floorpyproject.toml, as requires-python
Django rangepyproject.toml, as the django extra
PostgreSQL and MySQL serverstests/conftest.py, which is what starts them

A workflow cannot read a file to decide which container a service starts from or which versions a matrix holds, because both are settled before any step runs. Those keep a copy, and a test holds every copy to the place that decides it, so a version that drifts fails a test rather than a job.

What ships

Three kinds of artifact, each checked before it is published:

  • Native wheels, one per supported platform, carrying the compiled extension.
  • A portable wheel, carrying no compiled code, for anything else.
  • A source archive, for building from source.

A wheel ships a declared set of packages, so what it holds is decided by configuration. A source archive ships a directory, so what it holds is decided by what was lying in that directory. Both are read before release: the wheels for their contents, their licence, their type marker and their metadata, and the archive for what it needs and for anything that merely travelled with it.

What a release is held to

Every one of these runs before anything is published, and each is a gate rather than a report:

  • The full test suite, at complete statement and branch coverage, against real PostgreSQL and MySQL servers rather than recorded stand-ins.
  • Strict type checking under two checkers, and linting and formatting.
  • The Rust suite, its formatter, and its linter with warnings denied.
  • Five performance contracts, including throughput and statement counts for carrying out a fetch plan.
  • Every shipped example, run from an environment that installed the built package and nothing else.
  • The documentation site’s own check and its production build.
  • Dependency audits for both ecosystems, and a secret scan of the history.
  • A reproducible build: the wheel is built twice from one commit and the two have to be the same bytes. A build that differs run to run cannot be checked against a published hash by anyone who did not run it.

Publishing

A release happens on a version tag and on nothing else. Pushing to a branch runs the checks, and the checks cannot publish: they hold no publishing identity, and a test refuses one being added to them.

Tagging runs a separate workflow that builds the artifacts through the same definition the checks use, so what is published is built by the path that was verified rather than by a second copy of it.

It then does five things in order, and each has to succeed before the next begins:

  1. Builds every wheel and the source archive.
  2. Reads them with this project’s own contracts, and refuses a tag that does not name the version being published.
  3. Publishes to a test index.
  4. Installs from that index into a clean environment and imports the package. This is the only step that installs from an index rather than a directory, which is how everyone else will get it.
  5. Publishes the same files to the real index.

Steps three and five use trusted publishing. No API token is stored anywhere: the index is told which repository and which environment may publish, and a short-lived identity is issued to that job alone. Each of those two steps also sits behind a named environment, so a required reviewer can be asked for before either runs.

Nothing rebuilds between the test index and the real one. The files the second publishes are the files the first installed and imported.

Withdrawing a release

A published version is never deleted. Deleting one breaks every install that pins it and every lockfile that records its hash.

A release that should not be used is yanked instead, which leaves the files where they are so existing pins keep resolving, and stops the version being chosen by anything that did not ask for it by name. SECURITY.md carries the steps and the reporting process.
