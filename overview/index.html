What PyOQ is

A database first SQL toolkit for Python, and what it gives you.

PyOQ reads your database schema and writes Python for it. You then build SQL out of those generated names, and your editor knows every column, every type, and every table you can reach from here.

It is database first. The schema is the source of truth, not a set of model classes that hope to describe it. Change a column, regenerate, and the code that no longer matches stops type checking rather than failing at three in the morning.

Python
from pyoq.dsl import using
from application.database.tables import TITLES

rows = (
    using(database)
    .select(TITLES.ID, TITLES.NAME, TITLES.PRICE)
    .from_(TITLES)
    .where(TITLES.PRICE.gt(Decimal("10.00")))
    .order_by(TITLES.ID)
    .fetch_all()
    .into(TitleRow)
)

That reads as SQL, checks as Python, and returns a list of TitleRow. database is whatever you opened, and TITLES came from your schema. Your first query builds both from an empty file.

What you get

Types that come from your schema. TITLES.PRICE is a Decimal column because the database says so. Compare it to a string and the type checker stops you before the query runs.

Immutable query trees. Every builder returns a new object. Nothing you pass around can be changed underneath you, so a query held in a variable is the same query later.

Values that never reach the SQL. Everything you compare, insert, or update is bound as a parameter. There is no interpolation path to reach for, which is why there is no injection hole to remember to avoid.

Builders that cannot touch a database. pyoq.query builds statements and nothing else. That is what makes a query safe to construct anywhere, testable without a server, and cheap to pass between layers.

One place per fact. The dialects share a compiler, the frameworks share the core, and the schema has a single representation. There is no second copy to fall out of date.

What it is not

It is not an ORM. There are no model objects, no session-wide identity map, no lazy loading, and no session that decides when to write. Relation hydration uses an identity map only for one fetch, so joined rows can be assembled without merging distinct records. You still write the SQL, in Python, with types.

It is not a migration tool. PyOQ reads a schema; something else creates it. Under Django it reads your migration state directly, so the two stay in step without you keeping them there.

Where it runs

DatabasesSQLite, PostgreSQL, MySQL
FrameworksDjango, FastAPI, Sanic, or nothing at all
Stylessynchronous and asynchronous, both fully typed
Python3.11 and later

Asynchronous execution is available for PostgreSQL and MySQL. SQLite and the Django adapter use synchronous drivers. The asynchronous guide explains the boundary.
