Generating your types

Point PyOQ at a schema and read the package it writes.

Generation reads a schema and writes a Python package describing it. Nothing you write by hand goes in that directory: it is owned by the generator, and regenerating replaces it.

Tell PyOQ where things are

Configuration lives in pyproject.toml. Use a complete ${VARIABLE_NAME} reference when the connection string contains credentials.

Configuration
[tool.pyoq]
codegen-directory = "generated/database"
codegen-package = "application.database"
selected-profile = "default"

[tool.pyoq.profiles.default]
dialect = "postgres"
dsn = "${DATABASE_URL}"

[tool.pyoq.profiles.testing]
dialect = "sqlite"
database-path = "database/testing.sqlite"

A profile names a dialect and says where the database is: dsn for a literal connection string or environment reference, or database-path for a SQLite file. It cannot have both.

The configuration above uses the default flat layout. Its directory and import path remain unchanged.

Generate several databases

When one application uses several databases, opt into profile layout:

Configuration
[tool.pyoq]
codegen-layout = "profiles"
codegen-directory = "generated"
codegen-package = "generated"

[tool.pyoq.profiles.default]
codegen-name = "database"
dialect = "mysql"
dsn = "${MYSQL_DATABASE_URL}"
schema-snapshot = "schemas/database.json"

[tool.pyoq.profiles.analytics]
dialect = "postgres"
dsn = "${ANALYTICS_DATABASE_URL}"
schema-snapshot = "schemas/analytics.json"

Generate one database or every configured database:

Terminal
pyoq generate --profile default
pyoq generate --all-profiles
pyoq generate --all-profiles --check
pyoq generate --all-profiles --dry-run

The imports are independent:

Python
from generated.database.tables import CUSTOMER
from generated.analytics.tables import EVENT

One-profile generation touches only that profile’s package and ownership manifest. All-profile generation loads, renders, and validates every selected schema before publication. It stages the whole base and replaces it once, so a failure in any profile leaves every existing package unchanged.

Generate

Terminal
pyoq generate --project-root .

Two flags matter in a pipeline:

Terminal
pyoq generate --project-root . --check     # fails when the package is stale
pyoq generate --project-root . --dry-run   # reports what would change

Put --check in CI. It needs no credentials when the profile is a SQLite path or has a snapshot, and it turns “somebody forgot to regenerate” into a failed build.

What it writes

FileHolds
tables.pyone class per table, with a descriptor per column, its keys, and COLUMNS
rows.pya frozen dataclass per table, and one per key
writes.pytyped insert and update values, and their builders
relations.pya descriptor per foreign key, in both directions
enums.pyan enum per database enum type
domains.pya distinct type per database domain, over the type it is written on
routines.pya typed call per stored procedure and function
__init__.pyevery public name, re-exported

Reading it is the point. It is ordinary Python, formatted and lint clean, so you can open it and see exactly what PyOQ thinks your schema is.

Import descriptors from their concern module when the origin matters:

Python
from application.database.rows import TitlesRow
from application.database.tables import TITLES, Titles

The package root re-exports public generated names for convenience. The concern modules make ownership clearer in a large schema.

A generated routine carries the signature the catalog declared: its arity, its parameter types, the schema that keeps it, and the types its OUT and INOUT parameters answer with. A call that no longer matches the routine stops type checking rather than failing at the server.

Generation can read the schema from a recorded file instead of a database, which is what lets a check run with no credentials. See Snapshots and drift.

Regenerating is safe

The package is written to a staging directory and swapped into place, so a failed run never leaves half a package behind. A manifest records what generation owns; a file it does not own is never touched, and a file that has been edited by hand is reported rather than silently overwritten.

In profile layout, every database package has its own manifest. An ordinary --profile run cannot remove files owned by another profile. An --all-profiles run publishes all changed packages as one atomic base update.

Your editor may need a window reload the first time a generated package appears. The directory is replaced atomically, and some language servers miss that.

Generated builders

Every generated insert and update value is immutable. Its builder exposes one concrete method per writable column, which gives editors autocomplete without dynamic field lookup:

Python
values = Titles.builder().name("A Guide").price(Decimal("12.50")).build()

build() appears only after every required field has been set, and runtime checks enforce the same rule. The builder performs no database I/O. Use the positional insert DSL when SQL column order is clearer, and generated value objects when values are assembled across application layers.

Naming and collisions

Database names are converted deterministically into Python names. If two source names would produce the same Python name, generation raises NamingCollisionError and names both objects. It does not choose one based on catalog order. Resolve the collision in the schema or through the canonical naming policy before regenerating.

A normal development loop

  1. Change and apply the schema through your migration tool.
  2. Refresh the snapshot and generated package.
  3. Review both diffs.
  4. Run generation in check mode and run static checks.

See Migration lifecycle for Django, Alembic, and deployment ordering.

Under Django

There is no separate configuration, and no database is contacted. PyOQ reads your migration state, so the types follow the models you already maintain.

Terminal
python manage.py pyoq_codegen

The Django page covers the settings it reads and the optional makemigrations integration.
