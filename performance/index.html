Running statements

Performance

What costs what, and the knobs that matter before the ones that do not.

Where the time goes

Building a statement is cheap and happens once. Reading rows back happens per row, and that is where a slow application usually is.

PyOQ compiles a statement to SQL and a parameter tuple, then hands both to the driver. Nothing is re-derived per row: the types a row reads back as are worked out once, when the statement is compiled.

Read one thing, not many

The most expensive mistake is not a slow statement. It is a fast statement run once per row.

Python
# one query, then one per parent
for parent in database.many(select(PARENT_ID).from_(parents)):
    children = database.many(
        select(CHILD_ID).from_(children_table).where(PARENT.eq(parent[0]))
    )

Fetching across a relation is what avoids this. See Relations, which covers both strategies PyOQ plans: one joined query, and one query per level.

Writing many rows

A statement carries a bounded number of parameters, and the bound differs per dialect. Bulk writes split a large write into the fewest statements that fit, rather than one statement per row. See Bulk writes.

Streaming

many reads every row into memory. Where a result does not fit, stream it: a stream reads in batches and holds one batch at a time. See Transactions and streaming.

Pooling

A connection is expensive to open and cheap to reuse. Every dialect has a pool, and the framework integrations own one for the lifetime of the process rather than per request. See Standalone services and the framework guides.

Pool size is the one setting worth measuring rather than guessing. Too small and requests queue; too large and the database does the queuing instead. The connection guide covers sizing, checkout timeouts, and pool statistics.

Measuring rather than guessing

Diagnostics count statements per unit of work and report repeated shapes, which is how an N+1 shows up as a number rather than a hunch. A budget can refuse a unit of work that runs more statements than you meant to allow. See Diagnostics.

The native core

Row identity and grouping have a compiled implementation, used when it is available and falling back to the portable Python one when it is not. Both produce the same rows. Nothing you write chooses between them.

Set PYOQ_RUNTIME=python when you need to verify the portable path. Set PYOQ_RUNTIME=native when a deployment must fail rather than fall back. With neither set, selection is automatic.

The native boundary is reserved for measured kernels. Query semantics, dialects, generated types, and driver behavior stay in Python. This keeps native calls coarse enough to recover their boundary cost and keeps the portable implementation complete.

What to measure

Measure end-to-end work before micro-optimizing a builder:

  • statements per request or job;
  • repeated query shapes;
  • pool checkout pressure;
  • rows read and hydrated;
  • bulk statement count;
  • retained memory for gathered results.

Reducing one unnecessary round trip usually matters more than reducing the cost of constructing one expression node.

Before deployment

  • Run generation in check mode and run the application’s static type checks.
  • Open one pool per application process and connect its close operation to process shutdown.
  • Set a finite checkout timeout and observe checked-out connections.
  • Put query-count and repeat budgets around important requests or jobs.
  • Stream results that are not deliberately bounded in memory.
  • Test dialect-specific operations against the actual database family.
  • Exercise the portable runtime when a deployment platform may not receive a native wheel.

Statement timeouts are dialect-specific and do not replace application request deadlines. See Dialects for the precise boundary and Security for credential and statement-event handling.
