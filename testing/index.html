Testing applications

Checking generated code, compiled SQL, and database behavior in layers.

Test the smallest boundary that can prove the behavior. Query construction and compilation need no database. Driver behavior, transactions, locking, and dialect functions do.

Keep generated code current

Run generation in check mode before application tests:

Terminal
pyoq generate --project-root . --check

With a schema snapshot configured, this check needs no database credentials. It fails when a generated file is missing, changed, or stale. Run your normal Mypy, Pyright, or Ruff commands afterward so schema changes are reported at their call sites.

Django projects use their migration state:

Terminal
python manage.py pyoq_codegen --check

Test compiled SQL without a database

Builders are pure and immutable. Compile a statement directly when a unit test cares about query shape:

Python
from pyoq.query.sqlite import SQLiteCompiler

statement = (
    select(TITLES.ID)
    .from_(TITLES)
    .where(TITLES.NAME.eq("A Guide"))
)
compiled = SQLiteCompiler().compile(statement)

assert compiled.sql == (
    'SELECT "titles"."id" FROM "titles" '
    'WHERE ("titles"."name" = ?)'
)
assert compiled.parameters == ("A Guide",)

Assert parameters separately from SQL. A test that expects a value inside the SQL text would normalize unsafe behavior.

For portable query code, compile the same statement with PostgresCompiler, MySQLCompiler, and SQLiteCompiler, or test the capability rejection you expect from a particular dialect.

Test execution against the real dialect

SQLite in a temporary directory is useful for common execution behavior:

Python
def test_title_lookup(tmp_path):
    database_path = tmp_path / "test.sqlite"
    # create the schema, open a pool, run the query, then close the pool

Do not use SQLite as proof of PostgreSQL or MySQL behavior. Test returning clauses, JSON operators, arrays, routines, row locks, timeout handling, and transaction contention against the server that implements them. A container started for the test suite is usually the smallest reproducible boundary.

Test cardinality explicitly

Choose the terminal operation that states the expected number of rows:

Python
found = dsl.select(TITLES.ID).from_(TITLES).where(...).fetch_optional()
required = dsl.select(TITLES.ID).from_(TITLES).where(...).fetch_one()
all_rows = dsl.select(TITLES.ID).from_(TITLES).fetch_all()

Then test absence and duplication. fetch_one() must raise for both no rows and more than one row, while fetch_optional() permits only the first case.

Test query counts

Correct rows do not prove an efficient access pattern. Put a budget around one request or service operation:

Python
from pyoq.diagnostics import QueryBudget, QueryScope, ScopedOperations

scope = QueryScope(QueryBudget(maximum_queries=3))
database = ScopedOperations(operations, scope)

run_use_case(database)
assert scope.executions <= 3

This turns an N+1 regression into a failed test. Use relation fetch plans when the operation intentionally loads related rows. See Relations and Diagnostics.

Framework tests

FastAPI dependencies can be overridden with a substitute operations object. Sanic tests can attach a test database to the worker lifecycle. Django tests should use DjangoOperations on the test database so PyOQ participates in Django’s test transaction.

Avoid mocks that return rows without compiling or decoding them. They can prove application branching, but not that a statement is valid for the chosen dialect or that the declared result type matches the driver value.

A useful test split

  • Unit tests compile statements and check result-shaping code.
  • Contract tests run shared behavior against every supported dialect.
  • Integration tests cover driver errors, transactions, pools, and framework lifecycles.
  • Static checks compile application code against the generated package.

Each layer answers a different question. Passing one does not replace the others.
