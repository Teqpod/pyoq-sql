Connections and pools

Opening, sizing, observing, and closing database connection pools.

A pool owns database connections. A Database borrows one connection for each operation and returns it when the operation ends. Create it once for an application process, then leave its context during application shutdown.

Connect from a profile

With a profile in the current project’s pyproject.toml, connection and pool ownership are one context:

Configuration
[tool.pyoq.profiles.default]
dialect = "mysql"
host = "localhost"
port = 3306
database = "${MYSQL_DATABASE}"
username = "${MYSQL_USERNAME}"
password = "${MYSQL_PASSWORD}"
minimum-pool-size = 1
maximum-pool-size = 8
pool-checkout-timeout = 2.0
Python
from pyoq import connect
with connect(profile="default") as database:
    rows = database.select_from(TITLES).fetch_all()

Omit profile to use selected-profile. Configuration is read from pyproject.toml in the current directory. Use project_root=Path(...) when the application starts elsewhere, or config=Path("config/database.toml") for another file inside that root.

The same profile drives generation and runtime, so its dialect, connection, and pool policy are not repeated in application code. Pass an explicit pool_policy=PoolPolicy(...) only when one process needs to replace the entire profile policy.

Connect directly

Programs that do not have a project configuration can supply both values:

Python
from pyoq import Dialect, connect
from pyoq.config import DataSourceName
from pyoq.query.execution import PoolPolicy


policy = PoolPolicy(maximum_size=8)
with connect(
    DataSourceName("${DATABASE_URL}"),
    dialect=Dialect.POSTGRES,
    pool_policy=policy,
) as database:
    rows = database.select_from(TITLES).fetch_all()

The data source may be a string, SecretValue, or DataSourceName. DataSourceName("${DATABASE_URL}") resolves the environment variable while a literal DataSourceName stays literal. A direct data source requires dialect and cannot be mixed with profile arguments.

Construct the low-level components

Use the dialect-specific factories when an integration needs direct control of the pool or compiler:

Python
from pathlib import Path

from pyoq.query.execution import PoolPolicy
from pyoq.query.sqlite import SQLiteConnectionFactory, SQLiteExecutor, SQLitePool

policy = PoolPolicy(
    minimum_size=1,
    maximum_size=8,
    checkout_timeout=2.0,
)
pool = SQLitePool(SQLiteConnectionFactory(Path("application.sqlite")), policy)
database = SQLiteExecutor(pool)

minimum_size connections are opened when a synchronous pool is constructed. More are opened on demand, up to maximum_size. When all connections are in use, checkout waits for at most checkout_timeout seconds. Set the timeout to None only when an unbounded wait is an explicit operational decision.

PostgreSQL and MySQL use the same policy:

Python
from pyoq.query.postgres import (
    PostgresConnectionFactory,
    PostgresExecutor,
    PostgresPool,
)

pool = PostgresPool(PostgresConnectionFactory(database_url), policy)
database = PostgresExecutor(pool)

Use MySQLConnectionFactory, MySQLPool, and MySQLExecutor for MySQL. The complete framework-free MySQL application shows where the lifecycle lives in a multi-module project, how repositories share operations, and where transactions and shutdown belong.

Ownership and shutdown

connect() creates and closes its pool. Keep its context around the complete application run:

Python
with connect(profile="default") as database:
    rows = database.select_from(TITLES).fetch_all()

Long-running services should connect shutdown to their process or framework lifecycle. Standalone services, FastAPI, and Sanic show the appropriate owner for each environment. Django is different: the Django adapter borrows Django’s connection and does not create another pool.

Closing is idempotent. Idle connections close immediately. A checked-out connection closes when its lease returns. A new checkout after closure raises ConnectionPoolClosedError.

Pool exhaustion

If no connection becomes available before the checkout timeout, the operation raises ConnectionPoolTimeoutError. Treat that as capacity pressure, a leaked stream, or a transaction that remains open too long. Retrying immediately on the same saturated pool usually increases the pressure.

A stream and a transaction both keep one connection until their context exits:

Python
from pyoq.query.execution import StreamPolicy

with database.stream(statement, policy=StreamPolicy(batch_size=500)) as rows:
    for row in rows:
        consume(row)

Always leave those contexts promptly. Do not hold them open while making an unrelated network request or waiting for user input.

Pool statistics

Python
statistics = database.pool_stats

statistics.open_connections
statistics.idle_connections
statistics.checked_out_connections
statistics.closed

These values are a point-in-time view. Export them as gauges if pool pressure matters operationally. A pool that stays at its maximum with no idle connections is saturated even when no checkout has timed out yet.

Choosing a size

Start from the database connection budget, divide it across application processes, and leave room for migrations and administration. A service with several worker processes has one pool per process, so its possible connection count is workers * maximum_size.

A larger pool does not make the database faster. Increase it only when measurements show requests waiting for connections while the database still has capacity. See Performance and Diagnostics for the measurements around the pool.

Connection cleanup

Returning a connection rolls back unfinished work before it becomes idle. PostgreSQL and MySQL also clear the statement timeout applied by a previous operation. A connection that cannot be reset is discarded rather than handed to another caller in an unknown state.

Connection strings can contain credentials. Resolve them from configuration or an environment variable and never log them. See Configuration and Security.
