Transactions and streaming

Units of work, savepoints, and reading more rows than fit.

These examples take three things as given:

  • database is an open database, from a pool you opened or from the framework you are inside
  • dsl is using(database)
  • TITLES and its columns come from your generated package

Your first query builds all three from nothing.

A unit of work

Python
with database.transaction() as transaction:
    dsl = using(transaction)
    dsl.insert_into(...).values(...).execute()
    dsl.update(...).set(...).where(...).execute()

Leaving the block commits. An exception rolls back. There is no ambiguity about who decides, because the block that opened the transaction is the one that ends it.

Use the operations object yielded by the context. It owns the checked-out connection. Calling the outer database inside the block can borrow another connection, and that statement would not be part of this transaction.

Nesting

A transaction inside a transaction becomes a savepoint:

Python
with database.transaction() as transaction:
    using(transaction).insert_into(...).values(...).execute()

    with transaction.savepoint() as savepoint:
        using(savepoint).update(...).set(...).where(...).execute()
        # only this inner work is undone if it raises

The inner block can fail and be handled without losing the outer one.

Asynchronously

Python
async with database.transaction() as transaction:
    await using(transaction).insert_into(...).values(...).execute()

Same shape, same rules. The complete asynchronous setup is in Asynchronous execution.

Streaming

A result too large to hold is read in bounded batches rather than gathered:

Python
with database.stream(query) as rows:
    for row in rows:
        handle(row)

The stream holds a connection for as long as it is open, which is why it is a context manager: leaving the block gives the connection back. Reading from a stream after it is closed raises StreamStateError rather than returning nothing.

Set how much is buffered at a time when the default does not suit:

Python
from pyoq.query.execution import StreamPolicy

with database.stream(query, policy=StreamPolicy(batch_size=500)) as rows:
    ...

Inside a transaction, open the stream from the transaction object so it uses the same connection:

Python
with database.transaction() as transaction:
    with transaction.stream(query) as rows:
        for row in rows:
            handle(row)

Cancelling and bounding

Python
from pyoq.query.execution import CancellationToken, ExecutionControl

token = CancellationToken()
control = ExecutionControl(timeout=5.0, cancellation_token=token)

database.scalar(query, control=control)

A cancelled token is refused before the statement and after it. A timeout is applied where the backend has a way to honour it, and where it has none PyOQ does not pretend otherwise. See Dialects.

Holding the rows you read

A row you read inside a transaction can be changed by somebody else before you act on it. A lock holds it until the transaction ends:

Python
from pyoq.query import select

job_query = (
    select(JOBS.ID, JOBS.PAYLOAD)
    .from_(JOBS)
    .where(JOBS.STATE.eq("pending"))
    .limit(1)
    .for_update()
    .skip_locked()
)

with database.transaction() as transaction:
    job = transaction.one_or_none(job_query)
    if job is not None:
        process(job, transaction)

That is a work queue in one statement: each worker takes a row nobody else holds, and passes over the taken ones instead of queueing behind them. The transaction must stay open while the job state is changed, or the lock is released before it protects anything.

MethodHolds
for_update()the whole row
for_share()the row against change, while others may still read it
for_no_key_update()the row, leaving its key referenceable
for_key_share()only the key, against a change that breaks a reference

nowait() fails rather than wait for a row somebody else holds, and skip_locked() passes over it. Waiting is what a lock does when told neither. of(TABLE) narrows the lock to some of what the query read, which keeps a join from holding rows it only looked at. A field names its table just as well, so of(TITLES.ID) locks the table that column belongs to. The clauses read in the order SQL writes them.

A timed wait is in none of the three: FOR UPDATE WAIT is a syntax error on both PostgreSQL and MySQL, so PyOQ offers no way to ask for one.

Dialects differ, and each refuses what it has not got:

DialectLocking
PostgreSQLall four strengths, with NOWAIT, SKIP LOCKED, OF
MySQLfor_update() and for_share() only, with the same qualifiers
SQLitenone: it locks the whole database, so use a transaction

Stored functions and procedures have their own generated, typed contracts. See Stored routines. Pool lifecycle and sizing are covered in Connections and pools.
