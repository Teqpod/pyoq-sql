Your data

Relations

The graph generation derives, and fetching across it.

Generation reads every foreign key and writes a descriptor for it, in both directions, because a relation you can only follow one way is half a fact.

Python
from generated.relations import (
    CATALOG_TITLE_PUBLISHER_ID_FORWARD,   # a title to its publisher
    CATALOG_PUBLISHER_TITLE_REVERSE,      # a publisher to its titles
)

Each descriptor carries what the database said: the columns on both sides, the constraint name, the referential actions, the direction, the cardinality, and whether it is optional.

Direction and cardinality

TermMeans
Forwardfrom the table holding the key, to the one it points at
Reversethe same relation read the other way
To onethe far side is a single row, or none
To manythe far side is a collection

Cardinality is derived rather than declared: a foreign key whose columns are also a unique key is to-one in both directions, and otherwise the reverse side is to-many. Optionality follows from whether the key columns are nullable.

Fetching across a relation

Loading related rows one query at a time is the classic mistake, the N+1: a hundred parents becomes a hundred and one queries. PyOQ plans the fetch instead.

Python
from pyoq.relations import FetchPlan

A plan describes what to load and how, and the executor carries it out with a bounded number of statements. Related rows are gathered by key in batches, so the number of queries follows the number of relations you asked for, not the number of rows you got back.

How the plan is chosen

Planning across more than one query is what keeps the count bounded. A plan picks between two strategies per relation:

StrategyUsed whenCosts
joinedthe relation is to-oneone query, wider rows
select-ina to-many the dialect cannot gather inline, or one that is ordered or limitedone more query per relation level

Either way the number of statements follows the shape of what you asked for rather than the number of rows that came back, which is the whole point. Diagnostics counts them, so an N+1 that creeps back in shows up as a number rather than a suspicion.

Not loaded is not empty

A relation you did not ask for is not an empty list. Reading it raises RelationNotLoadedError, because “no publisher” and “you never asked for the publisher” are different facts, and quietly returning None for both is how data goes missing without anybody noticing.

Nested collections in one query

Where the dialect can do it, a to-many relation is gathered in the same query rather than a second one, using the server’s own JSON aggregation:

DialectUses
SQLitejson_group_array, needing 3.44 or later for ordering inside it
PostgreSQLjson_agg
MySQLJSON_ARRAYAGG, JSON_OBJECT

An empty relation comes back as an empty collection rather than a row of nulls. Where a dialect cannot order inside the aggregate, PyOQ says so rather than returning rows in an order it cannot promise.

Keeping only the first few

Where only the top of a collection matters, say how many. The rows kept are the ones the order put first, so a limit without an order is refused rather than answered with whichever few the database happened to reach:

Python
FetchRequest(relation, order_by=(by_column("published"),), limit=5)

MySQL cannot order rows inside an aggregate, so it cannot keep the ones an order chose either. A limited collection there is fetched with select-in instead, and asking for it nested is refused rather than answered with rows nobody picked.

Reading a table alongside the collection

A collection is the rows of one relation. A join widens what each of those rows carries without changing which rows there are, so a value from a second table can travel with them.

Python
from pyoq.relations import FetchJoin
from pyoq.schema import Identifier

FetchRequest(
    posts,
    order_by=(by_column("published"),),
    joins=(FetchJoin(author, (Identifier("display_name"),)),),
    limit=5,
)

The joined table is named by the relation that reaches it rather than by a table and a condition you write out, so the schema decides what can be joined. That relation is to-one: a to-many would change which rows there are, and is refused with a pointer to fetching it as a collection of its own. A plan is checked before it runs, so a join the schema cannot reach from the collection, or one carrying a column the joined table has not got, is a mistake reported against the schema rather than as SQL a server rejects.

When the executor carries the plan out, a joined table is read whole and comes back as a relation of each row of the collection, exactly like one reached any other way:

Python
for note in row.rows_of(notes):
    for topic in note.rows_of(topic_of_note):
        ...

A note whose join matched nothing reads as absent there, not as a row of nulls, which is the same answer a join in the parent’s own statement gives.

Reading collection_for directly instead, a joined column is carried under the name that appearance answers to, as pyoq_t2.title, because a collection may join one table twice and a row cannot carry one key twice. That is how a collection encodes its row so it can be read back, and the executor is what reads it.

Every such join is a left join. A join widens what each row carries and does not decide which rows there are, so a row whose join matched nothing stays and carries null for what the join would have added. An inner join would drop it, which is a row the collection was asked for going missing. That holds whether the relation is optional or not: a required relation still matches nothing when the row it points at is not there.

The rows are chosen first and the values are gathered after, which is what lets a limited collection carry a joined value: a join’s columns are not reachable through the single name a bounded set answers under, so the values travel out of it and the row is built where the aggregate is.

Turning a plan into a query

A resolved plan says what to fetch. collection_for turns one of its fetches into the node a dialect renders, which is the seam between knowing what a relation is and knowing what a collection looks like.

Python
from pyoq.fetching import collection_for
from pyoq.relations import resolve_fetch_plan

resolved = resolve_fetch_plan(plan, capabilities)
node = collection_for(resolved.fetches[0], (Identifier("title"),))

The columns each row carries are given rather than derived, because a caller asks for what it wants and a collection carrying every column would read more than was asked for. Nothing here reaches a database: it builds a node, the way every other builder in this toolkit does.

Saying what a collection is ordered by

Python
from pyoq.relations import by_column, by_expression

FetchRequest(
    employees,
    order_by=(by_expression("lower(name)"), by_column("id", descending=True)),
)

A column is checked against the related table, because the plan can see the schema. An expression is named rather than carried: a plan is built below the layer that writes queries and does not reach up into one. Naming it is enough to plan with, because what decides how a collection can be fetched is whether it is ordered at all, not what it is ordered by. The name is what the plan reports when it explains itself.

Running a plan

FetchExecutor carries a resolved plan out. It builds the statements, runs them, and hands back rows with their relations loaded.

Python
from pyoq.fetching import FetchExecutor

executor = FetchExecutor(operations, graph, maximum_parameters=999)
rows = executor.fetch(resolved, where=people.active.eq(True))

for row in rows:
    for note in row.rows_of(notes):
        ...

AsyncFetchExecutor is the same against a database that does not block:

Python
from pyoq.fetching import AsyncFetchExecutor

executor = AsyncFetchExecutor(operations, graph, maximum_parameters=999)
rows = await executor.fetch(resolved)

Both share one traversal. FetchAssembly decides what to run and what the answers mean, and asks for the rows of a query rather than running one, so the two executors differ only in how they ask. A plan therefore means the same thing either way, rather than meaning whatever two copies of the logic happen to agree on.

The parameter limit is given rather than read from the compiler, because a compiler is asked to compile and nothing else. It is the same limit a bulk planner is built with, and it decides how many parents one select-in statement can ask about.

What comes back is uniform. However a row arrived, joined into its parent’s row, gathered as JSON beside it, or read by a statement of its own, it is a row of its table in that table’s own column order, carrying its own relations the same way.

Reading a row as what it holds

values is what came back, and nothing there says which column is which, so it reads as object. A generated table constant carries the class its rows read back as, and a generated relationship constant carries the class the table it reaches reads back as, so reading through either keeps every declared type:

Python
team = row.read(TEAM)                       # TeamRow
team.name                                   # str

people = row.read_all(TEAM_PERSON_REVERSE)  # tuple[PersonRow, ...]
people[0].nick                              # str

The values came back in the order the table declares its columns, which is the order that class names its fields, so the row it builds holds each value under the name and the type its column was declared with.

A row is read through the table it came from, and only that one. It carries which table produced it, so a constant naming another is refused rather than believed: reading a row as a table it did not come from would put its values under names that were never theirs, and the type checker would agree.

Both sides of a relation constant carry their schema and catalog too. Two schemas may each hold a parent reaching a child over the same columns, and a constant that named only the tables would describe both of them.

A table written by hand names no row class and says so rather than guessing, the same way one names no columns and cannot be selected from without saying which. A relation nobody fetched raises when read by its constant, exactly as it does when read by its relation. Which strategy a dialect chose is not something the caller can see in the answer, which is the reason for choosing it below them.

Every relation is loaded for the whole result at once. A relation reached through a joined table is still one statement, not one per row, and a select-in is split only when a batch would exceed the parameter limit.

A to-one relation that resolved to nothing reads as absent, whether it was joined or read by a statement of its own, and whether it resolved to nothing because its key was null or because the row it named is not there. A to-many with no rows reads as an empty collection, because a relation with no children was answered rather than unanswered. A relation nobody fetched raises when read, which is the difference the three states exist to keep.

A parent whose key is null is not asked about at all. Null matches no row, including another null, so the question has an answer before it is asked.

Python
row.related[team].is_absent   # the join matched nothing
row.rows_of(notes)            # (), or the rows there were
row.rows_of(unfetched)        # raises RelationNotLoadedError

Reading one table more than once

Two relations to the same table, and a relation to the table it starts from, are ordinary shapes. An issue has a creator and a reviewer, both accounts. An employee has a manager and reports, both employees.

A statement keeps the name of the table it starts from and gives every other appearance a name of its own, numbered in the order the plan is walked. That is what a column is qualified by, because a column qualified by a table name says nothing when the statement reads that table twice.

SQL
SELECT "issue"."id", "pyoq_t1"."name", "pyoq_t2"."name"
FROM "issue"
LEFT JOIN "account" AS "pyoq_t1" ON ("issue"."creator_id" = "pyoq_t1"."id")
LEFT JOIN "account" AS "pyoq_t2" ON ("issue"."reviewer_id" = "pyoq_t2"."id")

A collection is given a name of its own for the same reason, and it matters more there. A collection of a table’s own rows correlates that table to itself, and without two names the correlation compares a table with itself and gathers nothing at all, on every dialect, without an error.

The names are fixed by the plan, so one plan always compiles to the same SQL. They also avoid every name the schema already uses. pyoq_t1 is a legal table name and a legal column name, and a generated name that took it would shadow the real one, so what the schema calls things is reserved and skipped.

Row identity

Hydrating a nested result means knowing which rows are the same row. That comes from the primary key where there is one, and PyOQ refuses to guess when there is not. See Column types for what identity is built from.
